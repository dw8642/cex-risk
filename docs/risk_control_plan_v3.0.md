## 1. 业务背景与建设目标

### 1.1 业务背景

市值管理 / 做市业务具有如下特点：

- 多交易所、多资产、多账户、多合作伙伴、多策略并行
- 存在代理执行链路，外部团队可能直接持有交易权限 API
- 交易权限、账户权限与风控责任集中在我方
- 风险不仅来自市场，还来自人、系统、AI 参与开发、安全攻击以及交易所平台规则约束

在 Crypto CEX 场景中，除传统交易风险外，还存在一类高危而容易被低估的风险：
- 平台规则违规（Wash Trade / OTR 超限）
- API 频控耗尽导致账号瘫痪
- 交易所临时维护 / 不可交易状态
- 多账户关联执行引发的平台审查风险
- 资金费率持续侵蚀与抵押物双杀
- **风控系统自身的误判反噬与隐性资金流失**

因此，单纯依赖交易监控或人工盯盘无法满足长期治理要求。

### 1.2 系统建设目标

本系统目标是建立一套覆盖**风险定义、风险观测、风险预警、基础控制、风险沉淀与持续演进**的统一风控平台。

**第一阶段的核心目标：**
1. 看得见风险、判得出风险、报得出风险、查得清风险
2. 对极端高危事件具备基础控制闭环，**同时保证控制动作不反噬业务**

**长期目标：**
1. 提高风险透明度，降低代理执行风险
2. 降低系统失明风险，降低平台违规风险
3. 建立可持续迭代的风险画像、规则优化与自动控制能力

### 1.3 AI 风险专项说明

> 本节说明为什么 AI 本身也是风险源，为后续识别层将 AI 纳入风险维度提供依据。

AI 已作为"开发效率放大器"介入代码、SQL、风控规则的生成，因此必须作为**系统风险放大器**纳入治理：

- **强制要求**：AI 生成代码必须人工 review；AI 生成规则必须双人审核；高危配置禁止 AI 直接发版上生产。
- **审计要求**：必须在配置系统/代码库中预留 AI 参与来源的标记。

## 2. 五层方法论总览

> 在进入各层详细设计之前，先建立方法论的整体认知框架。

本系统采用五层风控方法论，从基础方法论 **Define → Alert → Control → Learn** 演化而来：

| 层级 | 名称 | 核心问题 | 关键产出 | 对应版本 |
|------|------|---------|---------|---------|
| **L0** | 识别 Identify | 风险来自哪里？作用在谁？如何表现？ | 风险维度/对象/状态定义、四层治理模型 | 最小闭环 |
| **L1** | 监测 Monitor | 风险数据从哪来？数据可信吗？ | 实时数据流、新鲜度向量、Schema 校验 | MVP |
| **L2** | 预警 Alert | 风险是否正在发生？先救哪个？ | RiskEvent、82 条规则、仲裁结果 | MVP → V1.0 |
| **L3** | 控制 Control | 如何应对？代价几何？ | 控制动作（R0~R3）、审计日志 | V1.0 |
| **L4** | 演进 Evolve | 如何越来越好？ | 优化后的规则参数、自动校准的基线 | V2.0 |

五层方法论不是孤立的五个模块，而是一条**从被动到主动、从人工到自动**的演进链路。每一层都依赖前一层的输出作为输入：

```
识别（定义了"什么是风险"）
  ↓ 输出：风险维度、风险对象、风险状态定义、治理模型
监测（回答"风险数据从哪来"）
  ↓ 输出：实时数据流、新鲜度向量、Schema 校验结果
预警（回答"风险是否正在发生"）
  ↓ 输出：RiskEvent（含响应等级 P0~P3）、仲裁后的控制建议
控制（回答"如何应对风险"）
  ↓ 输出：控制动作执行记录、审计日志
演进（回答"如何越来越好"）
  ↓ 输出：优化后的规则参数、自动校准的基线 → 回馈到识别层和预警层
```

这意味着：如果识别层定义不清，监测层就不知道该采集什么数据；如果监测层数据不新鲜，预警层就可能误判；如果预警层缺乏仲裁，控制层就可能执行冲突的动作；如果控制层没有审计记录，演进层就无法回测和优化。

**层与层之间不是"做完一层再做下一层"**，而是在每个版本中逐步加深每一层的能力。例如：

- 最小闭环版本中，L0~L2 都只实现最基础的能力（1 条规则 + 1 个交易所）
- MVP 中，L0~L2 扩展到核心规则集，L3 开始引入基础控制动作
- V1.0 中，L2~L3 达到完整能力，L4 开始引入数据基座
- V2.0 中，L4 的回测和校准能力成熟，反馈到 L0 和 L2

## 3. 第一层 · 识别（Identify）

> **核心问题**：风险来自哪里？作用在谁身上？如何表现？
> **本层目标**：定义风控系统的"世界观"——什么算风险、谁承受风险、风险如何被观测。
> **下游依赖**：监测层依据本层定义来决定采集哪些数据；预警层依据本层的状态定义来设计规则。

### 3.1 风险定义的三层框架

本系统采用三层风险定义体系：
- **第一层：风险维度（Risk Dimension）** —— 回答：风险来自哪里
- **第二层：风险对象（Risk Object）** —— 回答：风险作用在谁或什么上
- **第三层：风险状态（Risk State）** —— 回答：风险当前如何表现、如何被识别

三者的关系是：一个风险维度的事件可能作用于多个风险对象，同时点亮多个风险状态。例如，"API Key 泄露"属于**安全维度**，作用于 **API Key 对象**，同时触发**权限状态风险**和**行为状态风险**。

### 3.2 风险维度定义

本方案在表达上采用五类风险维度：

1. **人的风险**（作恶、误操作、越权、利益转移、串通）
2. **系统的风险**（策略异常、数据延迟、风控链路失效、AI 错误输出）
3. **市场的风险**
   - *宏观行情风险*：插针、单边市、深度坍塌、脱锚
   - *微观结构风险*：毒性订单流、逆向选择、队列位置恶化
4. **安全与攻击风险**（Key 泄露、入侵、网络劫持、依赖投毒）
5. **平台规则与合规风险**（Wash Trade、OTR、API 滥用、平台惩罚与限制）

### 3.3 风险对象定义

> 识别了风险"来自哪里"后，还需要明确风险"作用在谁身上"。风险对象不是一个扁平列表，而是存在依赖链路——这决定了后续控制层的影响范围推算。

风险对象分为五层：

1. **核心业务风险对象**：外部合作伙伴、内部交易员、策略、API Key、资产、项目等。
2. **多账户治理对象**：账户组、项目组、策略组、同实际控制人集群。
3. **高权限技术治理对象**：架构师、运维、风控管理员自身。
4. **业务支撑与信息接口对象**：商务、客户经理。
5. **非人类与外部威胁对象**：AI 辅助开发链路、第三方依赖。

#### 3.3.1 风险对象依赖链路模型

上述五层对象并非扁平并列，在实际业务中存在明确的依赖与传播链路。系统必须理解并建模以下核心链路：

**链路一：Partner → API Key → Strategy → Account → Position**

这是最常见的执行链路。一个 Partner 持有多个 API Key，每个 Key 绑定不同策略并运行在不同账户上。当链路中任一节点发生风险事件时，需要沿链路进行**影响范围推算（Blast Radius Estimation）**：
- API Key 泄露 → 向下推算：该 Key 关联的所有策略和账户均进入风险状态
- 策略异常 → 向上追溯：确定由哪个 Partner 的哪个 Key 驱动；向下推算：影响了哪些账户和仓位
- 账户被平台限制 → 向上追溯：该账户所属 Partner 下的其他账户是否面临关联审查风险

**链路二：Account Group → 聚合敞口 → 平台合规审查**

多个账户可能属于同一个 `account_group`（见 3.6 多账户治理）。这些账户的聚合行为可能触发平台合规审查，因此风险对象之间存在"连坐传播"效应。

**链路三：人员 → 权限 → 配置 → 系统行为**

高权限人员（第 3 层对象）的操作可以直接改变风控系统的配置，从而影响系统对第 1、2 层对象的监控效果。这构成了一条"自上而下的治理链路"，也是内鬼风险的核心传播路径。

**工程要求**：
- MVP 阶段：在配置层建立 `Partner → API Key → Account` 的映射表，支持给定任一节点查询其上下游关联对象
- 二期：实现基于链路的自动影响范围推算，当某节点触发事件时，自动标记链路上其他节点的关注等级

### 3.4 风险状态定义

> 风险维度回答"来自哪里"，风险对象回答"作用在谁身上"，风险状态回答"此刻系统能观测到什么异常"。预警层的规则就是基于这些状态来触发的。

系统采用七类风险状态：

1. **权限状态风险**（如 API 过权、风控开关关闭）
2. **行为状态风险**（如非授权交易、多账户高相似执行）
3. **系统状态风险**（如心跳中断、API 频控耗尽、真相源冲突）
4. **市场状态风险**（如点差扩张、微观毒性上升）
5. **敞口状态风险**（如净 Delta 过高、群组聚合敞口超限）
6. **清算与生存风险**（如 MMR 过低、抵押物折价双杀）
7. **平台合规状态风险**（如 OTR 逼近红线、账户被平台限制）

#### 3.4.1 维度→状态多对多映射表

一个风险维度的根因事件可能同时点亮多个风险状态。以下矩阵显式定义了这种多对多映射关系（✓ 表示该维度可能直接触发该状态，○ 表示可能间接传导触发）：

| 风险维度 \ 风险状态 | 权限状态 | 行为状态 | 系统状态 | 市场状态 | 敞口状态 | 清算与生存 | 平台合规 |
|---|---|---|---|---|---|---|---|
| 人的风险 | ✓ | ✓ | ○ | | ○ | ○ | ✓ |
| 系统的风险 | ○ | ○ | ✓ | | ○ | ○ | ○ |
| 市场的风险 | | | ○ | ✓ | ✓ | ✓ | |
| 安全与攻击风险 | ✓ | ✓ | ✓ | | ○ | ○ | |
| 平台规则与合规风险 | ○ | ✓ | ○ | | | | ✓ |

**使用方式**：
- 当识别到某个根因事件属于特定维度时，系统应检查该维度对应的所有直接（✓）和间接（○）状态，评估是否存在连锁触发
- 规则设计时，同一根因事件应允许同时触发多个状态域的规则，而非要求"一个事件只归属一个状态"

> **与预警层的衔接**：预警层的规则编号体系（P/B/S/M/C/E/L）直接对应这七类风险状态。识别层定义了"什么状态算异常"，预警层定义了"异常到什么程度需要告警"。

### 3.5 四层风控治理模型

> 识别了维度、对象、状态之后，还需要一个**治理结构**来决定"谁管谁、规则怎么配、继承关系如何"。四层治理模型解决了"一套规则打天下"和"每个账户单独配置"之间的平衡问题。

```
Project (项目)
  └── Team (团队)
       └── Strategy (策略)
            └── Account (账户)
```

| 层级 | 定义 | 核心职责 | 示例 |
|------|------|---------|------|
| **Project** | 一个做市/市值管理项目 | 定义风险预算总额、合规要求、交易对白名单 | "BTC做市项目-币安" |
| **Team** | 执行该项目的团队 | 限定权限边界、预算份额、信任等级 | "内部量化组"、"PartnerA" |
| **Strategy** | 团队下的具体交易策略实例 | 定义行为基线、预期仓位范围、下单频率 | "mm-btc-binance-01" |
| **Account** | 策略运行的交易所账户 | 绑定 API Key、交易所、市场类型 | "币安合约账户-01" |

#### 3.5.1 层级可缺失规则

不是所有场景都有完整四层。系统必须支持层级缺失：

```
场景 A（完整链路）：Project → Team(内部量化组) → Strategy(mm-btc-01) → Account
场景 B（外部团队无策略）：Project → Team(PartnerA) → [跳过] → Account
场景 C（简单项目）：Project → [跳过] → [跳过] → Account
```

**数据模型表达**：每个下层对象通过外键指向上层。Strategy 和 Team 可以为 NULL，此时视为直接挂在更上一层。

#### 3.5.2 规则绑定与继承

规则可以挂在任何一层。检测时，从最具体的层级向上查找，**就近生效、上层兜底**。

```
规则解析优先级：Account > Strategy > Team > Project > 全局默认
```

**继承的特殊行为**：
- **enabled=false 在任何层级意味着"显式关闭"**：如果 Team 层关闭了某条规则，即使 Project 层启用了，该 Team 下的所有对象也不检测这条规则
- **config 部分覆盖**：下层只需要覆盖想改的参数，未覆盖的从上层继承。解析时逐层 merge
- **同一层级不同对象可以有不同配置**：Account-A 的 P-001 阈值可以和 Account-B 不同

> **与预警层的衔接**：预警层在执行规则时，先调用治理模型的规则解析函数，获取当前 Account 的生效规则集和参数，然后才执行检测逻辑。

### 3.6 多账户治理专题

> 多账户不是简单的"N 个账户"，而是一个风险黑洞：分散的同向敞口可能在聚合后超出风险预算，多账户高相似操作可能触发平台审查。本节为预警层的 C-Class 和 E-011 规则提供治理基础。

系统必须在底层建立：

1. **群组模型**：支持 `account_group`、`project_group` 绑定。
2. **聚合监控**：看清被切碎分散在各账户中的同向敞口和聚合预算消耗。
3. **同源分析**：识别同一策略模板在多个账户中的同质化踩踏行为。
4. **群组控制**：支持一键熔断某个 Partner 下的所有 Key，而非单一 Key。

## 4. 第二层 · 监测（Monitor）

> **核心问题**：风险数据从哪里来？数据可信吗？
> **本层目标**：建立可靠的数据采集管道，确保预警层的决策基于真实、及时、完整的数据。
> **上游依赖**：识别层定义了哪些风险维度和状态需要被观测，本层据此确定数据采集范围。
> **下游依赖**：预警层依赖本层输出的数据流和新鲜度信息来执行规则。

### 4.1 数据中心总体架构

> 监测层的数据采集管道分为**公共数据中心**和**私有数据中心**两个独立子系统，各自同时维护 WebSocket 订阅（实时流）和 REST 轮询（真相源快照）两条通道。两个数据中心的输出统一汇入 Kafka 数据总线，供下游指标引擎消费。

```
┌──────────────────────────────┐   ┌──────────────────────────────┐
│    公共数据中心（Public DC）   │   │    私有数据中心（Private DC）  │
│  ┌────────┐    ┌────────┐    │   │  ┌────────┐    ┌────────┐   │
│  │ WS 订阅 │    │REST轮询│    │   │  │ WS 订阅 │    │REST轮询│   │
│  │实时行情流│    │真相源快照│   │   │  │账户推送流│    │真相源快照│  │
│  └───┬────┘    └───┬────┘    │   │  └───┬────┘    └───┬────┘   │

**设计原则**：

1. **WS 用于实时检测，REST 用于真相源校验**——WS 提供毫秒级数据推送，是指标引擎的主要输入；REST 定时快照作为裁定依据，当 WS 数据存疑时以 REST 为准。
2. **公私分离**——公共数据（行情/深度/费率等）与私有数据（仓位/余额/订单等）在采集、存储、权限上严格隔离，私有数据中心需要 API Key 鉴权。
3. **每个 Ingestor 实例负责强 Schema 校验**——遇到未知/缺失字段立刻抛出 S-020 接入异常，防止脏数据污染下游。
4. **新鲜度追踪**——每条数据都携带 `received_at`（本地收到时间）和 `exchange_ts`（交易所时间戳），用于后续新鲜度向量计算。

### 4.4 交易所系统状态数据域

> 交易所自身不是一个稳定的黑盒，其系统状态直接影响风控判断的有效性。本节数据是预警层 S-017（临时不可交易）的核心数据源，也是打断"级联失效路径二"（交易所故障→误判→误杀）的关键。

必须覆盖：

- **交易所公告与维护计划**：通过交易所公告 API（如有）或定时爬取公告页，捕获计划内维护窗口、临时停机通知、交易对上下架信息。归属公共数据中心。
- **WebSocket 连接质量**：公共 WS 和私有 WS 各自独立监控——连接中断频率、重连次数、消息延迟（心跳 RTT）、数据缺口（gap）检测。
- **撮合引擎延迟推算**：通过下单到确认的往返延迟（私有 WS）、Orderbook 更新频率变化（公共 WS）来间接推测交易所撮合引擎是否出现性能劣化。
- **交易所已知异常模式库**：记录历史上各交易所出现过的故障模式（如某所 WS 断流但 REST 正常、某所在特定时间段撮合变慢），用于辅助异常归因。

**工程要求**：
- MVP 阶段：实现公共 WS + 私有 WS 连接质量监控（断连次数、重连频率、消息延迟）和交易所公告的基础抓取（至少覆盖主力交易所的系统状态公告）
- 二期：建立撮合延迟推算模型和历史故障模式库

### 4.5 策略元数据与行为基线数据域

> 风控规则的阈值不应全部硬编码，而应锚定在每个策略自身的**预期行为基线**上。本节数据为预警层 B-Class 和 E-Class 规则提供"什么是正常"的参考系——这是实现"千策千面"而非"一刀切"告警阈值的基础。

每个策略实例（Strategy Instance）应注册以下元数据：

| 字段 | 说明 | 示例 |
|---|---|---|
| `strategy_id` | 策略唯一标识 | `mm-btc-binance-01` |
| `strategy_type` | 策略类型 | `market_making` / `hedging` / `rebalancing` |
| `expected_position_range` | 预期持仓范围 [min, max] | `[-5 BTC, +5 BTC]` |
| `expected_order_rate` | 预期下单频率范围 | `[100, 500] orders/min` |
| `expected_otr_range` | 预期挂撤单比例范围 | `[3:1, 20:1]` |
| `expected_spread_range` | 预期报价价差范围 | `[0.02%, 0.15%]` |
| `max_single_order_size` | 单笔最大委托量 | `0.5 BTC` |
| `allowed_symbols` | 允许交易的交易对 | `[BTC/USDT, BTC/USDC]` |
| `allowed_exchanges` | 允许操作的交易所 | `[binance, okx]` |
| `hedging_pair_id` | 关联的对冲策略 ID（如有） | `hedge-btc-okx-01` |

**使用方式**：
- B-011（OTR 异常）的阈值不再是全局统一的硬编码值，而是参考该策略的 `expected_otr_range`，超出预期范围 N 倍时触发
- E-001（净 Delta 过高）的阈值参考 `expected_position_range`
- B-001（非授权交易）的判定参考 `allowed_symbols` 和 `allowed_exchanges`

**工程要求**：
- MVP 阶段：在策略配置表中增加上述元数据字段，规则引擎支持按 `strategy_id` 查询基线参数
- 二期：基于历史运行数据自动校准基线范围（异常检测自动调参）→ 这属于演进层（L4）的能力

### 4.6 真相源定义与容错原则

> 采集到数据后，还需要回答一个关键问题："当多个数据源冲突时，以谁为准？"——这决定了预警层的判断基础是否可靠。

- **核心原则**：**以交易所 REST 请求结果作为核心真相源。**
- **校验机制**：公共/私有两个数据中心各自的 WS 流用于实时检测，对应的 REST 通道用于状态核对与争议裁定。
- **异常降级**：若 WS 状态与 REST 状态大面积不一致，触发系统失明告警（S-013），并**锁定高级自动控制动作**，防止乱砍。
- **公私独立判定**：公共数据中心和私有数据中心的 WS/REST 一致性分别独立评估——公共侧失明不自动认定私有侧也失明，反之亦然。

#### 4.6.1 REST 真相源时效性边界

> REST 快照本身存在查询延迟和一致性问题，在高频场景下不能无条件视为"绝对真相"。本节的时效性分级直接影响控制层的决策权限——数据越陈旧，允许执行的控制动作越温和。

| REST 快照年龄 | 可信度等级 | 允许的决策范围 |
|---|---|---|
| < 2 秒 | **鲜活（Fresh）** | 可用于所有自动控制决策 |
| 2–10 秒 | **可参考（Stale-Warning）** | 可用于告警触发，但自动阻断类动作需要二次确认（再查一次 REST） |
| 10–60 秒 | **陈旧（Stale）** | 仅用于趋势参考，禁止用于任何自动控制动作 |
| > 60 秒 | **过期（Expired）** | 视为数据缺失，触发 S-013 系统失明告警 |

**实现方式**：
- 每条 REST 快照数据必须携带 `fetched_at` 时间戳
- 规则引擎在读取状态数据时，首先检查 `fetched_at` 与当前时间的差值，根据上表决定该数据的可用范围
- 若关键数据（仓位、余额、保证金率）的快照年龄进入"陈旧"或"过期"状态，自动触发一次强制 REST 刷新

**注意**：上述时间阈值为建议初始值，需根据交易所实际 REST 响应延迟和业务频率进行校准。不同交易所的 REST 性能差异可能很大，应支持按交易所维度配置。公共 REST 和私有 REST 的时效阈值可能不同（公共行情延迟容忍度更高）。

#### 4.6.2 部分数据新鲜的混合状态处理（V2.5 新增）

> 生产环境中，不同数据维度的 REST 快照新鲜度往往不一致。本节的处理规则与控制层的动作可逆性分级（5.3.3）直接联动——数据越不确定，允许执行的动作可逆性等级越高（越温和）。

**数据新鲜度向量**：

规则引擎在做决策时，将当前各数据维度的新鲜度视为一个向量，而非单一标量。公共侧和私有侧的新鲜度分别追踪：

```
freshness_vector = {
    // 私有数据中心
    position:    Fresh      (0.8s ago)
    balance:     Fresh      (1.2s ago)
    margin_rate: Stale-Warning (4s ago)
    orders:      Stale      (12s ago)
    // 公共数据中心
    mark_price:  Fresh      (0.3s ago)
    orderbook:   Fresh      (0.5s ago)
    funding:     Fresh      (8s ago)
}
```

**按决策类型定义最低新鲜度要求**：

| 决策类型 | 必须 Fresh 的数据维度 | 允许 Stale-Warning 的维度 | 不可 Stale/Expired 的维度 | 示例 |
|---|---|---|---|---|
| **自动平仓/减仓（R0/R1 动作）** | position + balance + mark_price | margin_rate | 全部 | L-001 触发后的自动减仓 |
| **暂停策略（R2 动作）** | position | balance, margin_rate | position | E-001 触发后暂停下单 |
| **告警触发（R3 纯观测）** | 无硬性要求 | 全部允许 | 无 | B-010 Wash Trade 嫌疑 |
| **对账任务** | 无（离线批量任务） | 全部允许 | 无 | E-014 周期对账 |

**处理逻辑**：

1. 规则引擎触发某个事件后，根据该事件对应的控制动作类型，查表获取最低新鲜度要求
2. 检查 `freshness_vector` 中相关维度是否满足要求
3. 若满足 → 正常执行控制动作
4. 若不满足 → 立即触发该维度的强制 REST 刷新（通知对应数据中心），等待刷新结果（设超时上限，如 3 秒）
5. 刷新后仍不满足 → 将控制动作降级一档可逆性（R0→R1, R1→R2），同时升级人工告警
6. 若刷新超时 → 视为该维度数据缺失，按 4.6.1 的 Expired 规则处理

## 5. 第三层 · 预警（Alert）

> **核心问题**：风险是否正在发生？多个风险同时发生时先救哪个？
> **本层目标**：基于监测层的数据流，执行规则检测，生成 RiskEvent，并通过仲裁引擎决定响应优先级。
> **上游依赖**：监测层提供的实时数据流和新鲜度向量；识别层定义的治理模型和规则绑定。
> **下游依赖**：控制层接收本层输出的 RiskEvent 和控制建议来执行动作。

### 5.1 事件响应等级标签体系

> 事件编号（P/B/S/M/C/E/L）按风险类型分类，用于识别和归因。但运维需要快速判断"先救哪个"，因此在类型分类之上叠加**响应等级标签**，两者正交、互不替代。

| 响应等级 | 含义 | 响应时效要求 | 典型事件 |
|---|---|---|---|
| **P0-Critical** | 不可逆损失正在发生或即将发生 | < 1 分钟自动响应 + 即时人工通知 | L-001 MMR 过低、P-006 大额异常提币、S-013 系统全面失明 |
| **P1-Urgent** | 高危状态已形成，短期内可能升级为 P0 | < 5 分钟人工确认 | S-016 频控耗尽、E-001 净 Delta 严重超限、C-004 账户被限制 |
| **P2-Warning** | 异常趋势已出现，需要关注和干预 | < 30 分钟人工确认 | B-010 Wash Trade 嫌疑、E-010 Funding Rate 异常、M-002 深度骤降 |
| **P3-Info** | 信息性告警，用于审计追溯 | 日报/周报汇总 | E-014 对账微小差异、B-011 OTR 轻微偏高 |

**分配规则**：
- 每个事件 ID 有一个**默认响应等级**（见下方事件清单）
- 响应等级可根据严重程度动态升降（如 E-001 净 Delta 轻微超限为 P2，严重超限为 P1）
- 告警展示和通知渠道按响应等级区分：P0 电话+IM 群@all，P1 IM 群@值班，P2 IM 推送，P3 仅记录

### 5.2 风险事件库（核心清单）

> 以下规则覆盖了识别层定义的全部七类风险状态（完整规则库共 71 条，详见 `rule_library_v3.0_checklist.md`）。每条规则的阈值锚定来自监测层 4.5 的策略元数据基线。规则所需指标由指标引擎（8.3）产出，规则评估由规则引擎（8.4）按 F0~F4 时间分层执行。

#### 5.2.1 权限类 (P-Class)

> 对应识别层的"权限状态风险"。这类规则的目的是检测 API Key 权限是否超出最小必要范围、是否存在异常提币/划转行为。

- **P-001** 提币权限异常开启 — **默认 P1**
- **P-002** 非授权交易范围开放 — **默认 P2**
- **P-004** 高危 API Key 未及时停用 — **默认 P1**
- **P-005** 多账户权限过度扩散风险 — **默认 P2**
- **P-006** 大额/异常提币实时监控 — **默认 P0**
  - 触发条件：单笔提币金额 > 阈值（按资产配置），或短时间（如 30 分钟内）累计提币次数 > N 次，或提币目标地址不在已登记白名单中
  - 识别方式：实时监听交易所提币 API / WS 推送 + 定时 REST 轮询 Withdrawal History
  - 说明：E-014 对账差异是事后发现机制，P-006 是事中拦截机制，两者互补而非替代
- **P-007** 异常资金划转监控 — **默认 P1**
  - 触发条件：主子账户间异常划转（金额异常、频率异常、非计划内划转）、划转到未登记子账户
  - 识别方式：监听 Internal Transfer API + Ledger 对账

#### 5.2.2 行为类 (B-Class)

> 对应识别层的"行为状态风险"。这类规则的阈值大量依赖监测层 4.1.2 的策略元数据基线——例如 B-011 的 OTR 阈值参考策略的 `expected_otr_range`，而非全局硬编码。

- **B-001** 非授权交易 — **默认 P1**
- **B-003** 高成交低净仓变化 — **默认 P2**
- **B-007** 对敲 / 刷量嫌疑（基础版） — **默认 P2**
- **B-010** Wash Trade / 内部自成交风险 — **默认 P2**（确认后升 P1）
- **B-011** 挂撤单比例（OTR）异常 — **默认 P2**
- **B-012** 多账户高相似执行行为风险 — **默认 P2**
- **B-013** 单腿暴露（Leg Risk）监控 — **默认 P2**（超时未对冲升 P1）
  - 触发条件：做市或对冲策略的一条腿成交后，另一条腿在预设时间窗口内未成交或未完全成交
  - 监控指标：`leg_exposure_amount`（未对冲暴露金额）、`leg_exposure_duration`（暴露持续时间）、`leg_fill_ratio`（对冲腿成交比例）
  - 与 E-001 的区别：E-001 监控最终持仓的净 Delta 结果，B-013 监控对冲执行**过程中**的暂态暴露。E-001 可能因偏差互相抵消而不触发，但 B-013 会捕获瞬间大额暴露
  - 阈值锚定：参考策略元数据中的 `hedging_pair_id`，关联两个策略实例的执行时序
  - 分级：暴露金额 < 预算 10% 且持续 < 30 秒 → P3 记录；暴露金额 > 预算 30% 或持续 > 2 分钟 → P1 升级

#### 5.2.3 系统与接入类 (S-Class)

> 对应识别层的"系统状态风险"。这类规则的数据来源高度依赖监测层 4.1.1 的交易所系统状态数据域和 4.2 的真相源时效性机制。

- **S-001** 策略心跳超时 — **默认 P1**
- **S-007** 数据真相源不一致 — **默认 P2**（大面积不一致升 P0）
- **S-013** 风控系统整体失明风险 — **默认 P0**
- **S-014** Watchdog 发现主风控链路异常 — **默认 P0**
- **S-016** API 频控使用率过高 / 耗尽风险 — **默认 P1**
- **S-017** 交易所/特定 Symbol 临时不可交易 — **默认 P1**
- **S-018** 群组控制失效（仅部分账户被控制） — **默认 P1**
- **S-020** API 契约漂移与静默变更风险 — **默认 P1**

#### 5.2.4 市场与微观结构类 (M-Class)

> 对应识别层的"市场状态风险"。注意：市场本身不可控，因此 M-Class 规则的控制动作建议通常比较温和（R2/R3 为主），重点在于提前预警。

- **M-002** 深度骤降 — **默认 P2**
- **M-004** 跨所价格偏离 — **默认 P2**
- **M-007** 毒性订单流 / 逆向选择急剧恶化 — **默认 P2**

#### 5.2.5 平台合规类 (C-Class)

> 对应识别层的"平台合规状态风险"。这类规则依赖识别层 3.6 多账户治理的群组模型来判断账户间的关联行为。

- **C-001** 多账户关联执行触发平台合规审查风险 — **默认 P2**
- **C-002** 多账户集群规避平台限流/限额风险 — **默认 P2**
- **C-004** 账户被平台实施交易限制/降权风险 — **默认 P1**

#### 5.2.6 敞口与对账类 (E-Class)

> 对应识别层的"敞口状态风险"。E-Class 的特点是既有实时监控（E-001），也有周期性对账（E-014）。E-015 是 E-006 的**前置预警**——在预算超限之前通过消耗速率提前告警。

- **E-001** 净 Delta 过高 — **默认 P2**（严重超限升 P1）
- **E-006** 风险预算超限 — **默认 P2**
- **E-010** Funding Rate Bleed（资金费率持续侵蚀） — **默认 P2**
  - **E-010a 累积侵蚀**：过去 N 个结算周期的累积 Funding 成本超过阈值（按持仓本金百分比）— P2
  - **E-010b 结算跳变**：下一个结算时刻的预期费率与当前费率偏差 > 阈值，或绝对值突然飙升 — P2（极端值升 P1）
  - **E-010c 预期偏差**：实际结算费率与结算前 T-5min 的预期费率偏差 > 阈值，说明费率预测模型失效或市场结构突变 — P2
- **E-011** 账户组聚合敞口超限 — **默认 P2**（严重超限升 P1）
- **E-014** 资金周期对账差异与隐性流失风险 — **默认 P2**（大额差异升 P1）
- **E-015** 风险预算消耗速率异常（V2.5 新增）— **默认 P2**（极端加速升 P1）
  - 背景：E-006 监控预算**绝对消耗量**，E-015 监控**消耗速率**——速率比绝对值更能提前预警
  - 监控指标：`budget_burn_rate`（滚动窗口内预算消耗占日预算百分比）、`budget_burn_acceleration`（消耗速率变化率）、`budget_remaining_runway`（按当前速率推算的剩余时间）
  - P2 触发：`budget_burn_rate`（1h 窗口）> 日预算 25%，或 `remaining_runway` < 4 小时
  - P1 升级：`budget_burn_rate`（30min 窗口）> 日预算 20%，或 `remaining_runway` < 2 小时，或 `acceleration` 连续 3 窗口为正
  - 控制动作建议：E-015 触发时不自动执行阻断，而是通知值班人员评估当前策略状态

#### 5.2.7 清算类 (L-Class)

> 对应识别层的"清算与生存风险"。L-Class 是所有规则中优先级最高的——在仲裁引擎中，清算风险永远排在第一位。

- **L-001** 维持保证金率（MMR）过低 — **默认 P0**
- **L-004** ADL 风险升高 — **默认 P1**
- **L-006** 联合保证金/非稳定币抵押物折价双杀风险 — **默认 P1**

### 5.3 风险状态仲裁机制

> 当多个规则同时触发，且对应的控制动作存在冲突时（例如"应该撤单"和"不能消耗 API 配额"同时成立），需要仲裁引擎来决定"先做什么、不做什么"。本节是预警层与控制层的桥梁。

#### 5.3.1 状态优先级排序

当系统需要在多个并发风险状态间做取舍时，遵循以下优先级（从高到低）：

1. **清算与生存风险**（L-Class）—— 最高优先级，涉及不可逆资金损失
2. **系统状态风险中的"失明"类**（S-013, S-014）—— 失明意味着后续所有判断不可信
3. **安全相关的权限状态风险**（P-001, P-004 等涉及 Key 泄露/提币权限的）
4. **敞口状态风险**（E-Class）
5. **平台合规状态风险**（C-Class）
6. **行为状态风险**（B-Class）
7. **市场状态风险**（M-Class）—— 市场本身不可控，优先处理可控的内部状态

#### 5.3.2 核心冲突场景与仲裁规则

**冲突一：系统失明 vs 敞口/清算风险同时触发**
- 仲裁结论：系统失明时，数据不可信 → **锁死所有基于数据判断的自动控制动作**，仅保留"已确认真实"的最后一次 REST 快照作为参考，转入 P0 人工告警
- 原因：在数据不可信的状态下执行自动平仓/吊销可能造成更大损失

**冲突二：频控耗尽 vs 需要执行紧急阻断**
- 仲裁结论：进入"配额保命模式"（见第 6 节保命约束 4），将仅剩 API 额度**专供**最高优先级的阻断动作（Key 吊销 > 撤单 > 查仓）
- 降级策略：非关键查询全部暂停，仅执行与 L-Class / P-Class 相关的 API 调用

**冲突三：多个账户同时触发不同等级风险**
- 仲裁结论：按账户所属 `account_group` 聚合评估，优先处理影响范围（Blast Radius）最大的群组
- 若群组内既有 L-Class 又有 B-Class：先处理 L-Class 账户的清算风险，再处理 B-Class 的行为异常

#### 5.3.3 动作可逆性作为仲裁次级考量（V2.5 新增）

> 状态优先级（5.3.1）决定"先处理谁"，动作可逆性决定"用什么手段处理"。这里定义的可逆性等级直接传递给控制层执行。

**控制动作可逆性分级**：

| 可逆性等级 | 含义 | 典型动作 | 恢复代价 |
|---|---|---|---|
| **R0-不可逆** | 执行后无法自动回滚 | API Key 吊销、强制市价平仓 | 分钟~小时级人工操作 |
| **R1-高代价可逆** | 技术上可回滚，但有业务损失 | 撤销全部挂单（丢失队列优先级） | 秒~分钟级，伴随隐性成本 |
| **R2-低代价可逆** | 可快速回滚，业务影响可控 | 暂停策略下单、降低报价频率 | 秒级，几乎无损 |
| **R3-纯观测** | 不执行控制动作 | 升级告警等级 + 电话通知值班 | 零 |

**仲裁中的应用规则**：

1. **默认原则**：同一风险状态下存在多种可选控制动作时，优先执行可逆性等级更高（R2/R3）的动作，仅在未能遏制风险升级时才降级到 R1/R0
2. **P0 例外**：风险已确认为 P0-Critical（如 L-001 MMR 触及强平线、P-006 确认的大额异常提币），允许直接执行 R0 不可逆动作
3. **数据不确定时的强制约束**：系统处于数据可信度降级状态（REST 快照为 Stale-Warning 或更差），禁止执行 R0，最多执行到 R1，同时必须触发 P0 人工告警

**典型应用场景**：

- 策略净 Delta 超限（E-001，P2）→ 第一响应：R2 暂停该策略新增下单 → Delta 继续恶化升级到 P1 → 第二响应：R1 撤销该策略全部挂单 → Delta 仍未收敛且逼近清算线 → 升级 P0 → R0 人工审批后强制减仓
- 疑似 API Key 泄露（P-001，P1）但尚未确认 → 第一响应：R2 暂停该 Key 关联的所有策略 + R3 升级到 P0 通知 → 人工确认后 → R0 吊销 Key

### 5.4 关键级联失效路径

> 以下级联模式是生产中最可能出现的"多米诺骨牌"效应。理解这些路径的意义在于：当值班人员收到一个告警时，能快速判断是否正在发生级联失效，从而采取更全面的应对措施。

**路径一：频控耗尽 → 风控致盲 → 清算失控**
```
S-016 API 频控耗尽
  → 风控无法执行 REST 查询刷新真相源
  → S-013 系统失明
  → L-001 MMR 过低 无法被及时发现
  → 清算/ADL 发生
```
核心矛盾：风控系统自身消耗 API 配额（查仓、查余额）可能加速频控耗尽。
应对要点：进入配额保命模式时，风控查询频率必须大幅降低，而非停止。

**路径二：交易所故障 → 数据断流 → 误判触发错误控制**
```
S-017 交易所临时不可交易
  → WS 数据断流，但未被识别为交易所故障
  → S-007 真相源不一致（WS 停更 vs REST 陈旧数据）
  → 规则引擎基于脏数据触发 E-001 或 L-001
  → 自动阻断动作误杀正常业务
```
应对要点：监测层 4.1.1 交易所系统状态数据域就是为打断这条链路设计的——如果已知交易所在维护，则相关规则应自动进入静默/降级模式。

**路径三：Wash Trade → 平台处罚 → 账户限制 → 仓位无法平仓**
```
B-010 Wash Trade 发生（可能无意）
  → 平台检测并处罚
  → C-004 账户被限制（禁止新增开仓，或交易功能全面冻结）
  → 存量仓位无法正常平仓/对冲
  → E-001 敞口失控 + L-001 清算风险上升
```
应对要点：B-010 检测不应仅用于事后审计，而应尽可能在 Wash Trade 行为累积到平台处罚阈值之前发出预警。

**路径四：单腿暴露 → 敞口偏移 → 资金费率侵蚀放大**
```
B-013 单腿暴露持续
  → E-001 净 Delta 偏移
  → 若方向恰好是 Funding Rate 不利方向
  → E-010 资金费率侵蚀加速
  → 长期侵蚀叠加仓位亏损 → L-001 清算风险
```
应对要点：B-013 的超时升级机制应在单腿暴露方向与当前 Funding Rate 方向一致（不利）时更快触发升级。

**工程要求**：
- MVP 阶段不要求自动关联检测，但运维文档和告警处理 SOP 中必须明确标注这些路径
- 二期：实现级联失效自动关联检测

## 6. 第四层 · 控制（Control）

> **核心问题**：如何应对风险？代价几何？如何防止控制动作本身成为新的风险源？
> **本层目标**：执行预警层仲裁后的控制建议，同时确保控制动作不反噬业务。
> **上游依赖**：预警层输出的 RiskEvent（含响应等级和控制建议）；监测层的数据新鲜度向量（决定允许执行的动作级别）。

### 6.1 为什么不承诺"逐笔前置拦截"

> 理解这个约束对于正确设定对系统的预期至关重要。

外部团队直连交易所 API 架构下，风控没有统一网关，因此系统定位为：**具备事中快速基础控制闭环，而非 Pre-trade 网关。**

### 6.2 控制动作分层

> 三层控制动作从事前到事后形成完整闭环。

1. **权限前置约束**（事前）：API Scope 最小化、IP 白名单、平台风险预算配置。
2. **事中快速控制**（事中）：API Key 紧急吊销、策略状态强制切换、触发人工接管。动作的选择遵循预警层 5.3.3 的可逆性分级。
3. **事后治理闭环**（事后）：审计、复盘、平台惩罚溯源。审计数据同时馈入演进层用于规则回测。

### 6.3 核心保命机制：防风暴与防反噬（Blast Radius Control）

> 这是控制层最关键的自我约束——如果风控系统"发疯"吊销所有业务 Key，造成的损失可能比不做风控还大。

- **全局动作限流（Token Bucket）**：设定"每 N 分钟最多执行 X 次高危动作"的熔断阀值。
- **盲区自动降级**：当识别到数据大面积断流（S-008）或真相源冲突（S-007）时，系统必须**锁死**自动吊销逻辑，转为纯人工 P0 告警审批。

### 6.4 工程落地"保命"硬性约束

> 这 4 条是系统上线前最容易踩坑的生死线，开发与测试必须严格验收。

**约束 1：防控制动作反噬（Blast Radius Control）**
- 不允许无限制的自动阻断。必须配置全局动作令牌桶（如：5分钟内最多吊销 3 个 Key）。
- 数据源大量报错时，自动阻断必须降级为人工告警。

**约束 2：周期资金对账机制（Asset Reconciliation Task）**
- 严禁仅靠 Order Fills 累加计算资产。
- 必须有独立的 T+1 或 H+1 任务，拉取交易所底层 `Ledger / Wallet History` 进行对账，捕获由于资金费率、不明提币、主子账户划转造成的"隐性资金流失"。

**约束 3：API 契约漂移防护（Schema Drift Validation）**
- 交易所随时可能静默修改 API 字段。
- Ingestor 解析层必须有强 Schema 校验，遇到未知/缺失字段立刻抛出 `S-020` 接入异常，**绝不允许携带脏数据进入计算引擎污染全局状态**。

**约束 4：频控保命降级策略（Rate Limit Degradation）**
- 当 API Weight 使用率达到 90% 时，系统不能简单发起海量撤单（会加速封号）。
- 必须进入"配额保命模式"：停止无关查仓/改单，将仅剩的 API 额度留给最关键的风险阻断动作。

## 7. 第五层 · 演进（Evolve）

> **核心问题**：如何让系统越来越好？如何从"人工调参"走向"数据驱动"？
> **本层目标**：基于控制层的执行记录和监测层的历史数据，持续优化规则参数和策略基线。
> **上游依赖**：监测层持久化的私有数据（orders/fills/ledger）；控制层的执行审计日志；预警层的历史告警记录。
> **下游反馈**：优化后的规则参数回馈到预警层；校准后的策略基线回馈到监测层。

### 7.1 为什么需要独立的演进层

> 没有演进层，系统就是一个"静态规则引擎"——规则上线后参数永远不变，直到人工发现问题并手动调整。而做市场景下，市场结构在变、策略行为在变、交易所规则在变，静态参数一定会逐渐失效。

演进层的价值在于：
1. **规则失效检测**：某条规则上线后一直不触发，可能是阈值设得太松，也可能是场景已经不存在
2. **误报降低**：分析历史告警中的误报案例，发现阈值设置不合理的规则
3. **基线漂移适应**：策略的正常行为范围会随市场环境变化，基线需要定期校准
4. **新规则发现**：从历史数据中发现未被现有规则覆盖的异常模式

### 7.2 Evolve 能力金字塔

> 演进层的能力分为四级，每一级依赖前一级的数据基座。

| 层级 | 名称 | 说明 | 对应版本 |
|------|------|------|---------|
| **E-L0** | 数据采集 | orders / fills / ledger → ClickHouse 全量持久化 | 最小闭环 |
| **E-L1** | 审计溯源 | 交易回放、异常取证、合规审计 | MVP |
| **E-L2** | 规则回测 | 历史数据验证规则有效性，优化阈值 | V1.0 |
| **E-L3** | 基线校准 | 策略行为基线自动学习与校准 | V2.0 |
| **E-L4** | 自动决策 | 异常模式自动识别与响应（远期） | V2.0+ |

**E-L0 数据采集**是整个金字塔的基座——没有历史订单/成交数据的全量持久化，上层的回测、校准、自动决策能力就无从谈起。这就是为什么在架构设计中必须从最小闭环版本就开始做私有数据订阅和存储。

### 7.3 演进层如何反馈到其他层

```
演进层（E-L2 规则回测）
  → 发现 B-011 OTR 阈值对做市策略偏紧（误报率 35%）
  → 建议将阈值从 20:1 调整为 30:1
  → 反馈到预警层的 B-011 规则配置

演进层（E-L3 基线校准）
  → 发现 mm-btc-binance-01 的 expected_position_range 近 30 天均值偏移
  → 自动更新监测层 4.1.2 的策略元数据基线
  → 预警层的 E-001 阈值随之自动调整
```

这种反馈机制使整个系统形成闭环：识别→监测→预警→控制→演进→（回馈到）识别/监测/预警。

**三级管道的核心约束**：

1. **单向数据流**：Data → Indicator → Rule，严禁反向依赖（规则引擎不直接读原始数据，指标引擎不直接触发控制动作）。
2. **Redis 作为级间接口**：指标引擎将计算结果写入 Redis，规则引擎从 Redis 读取指标值。Redis key 命名规范：`ind:{indicator_id}:{entity_grain_values}`，如 `ind:IND-L-001:binance:BTC-USDT:acct001`。
3. **Kafka 作为事件驱动桥梁**：T0/F0 类实时指标和规则通过 Kafka 事件触发，而非轮询 Redis。
4. **ClickHouse 旁路归档**：每一级的数据都同步写入 ClickHouse 用于演进层回测，但不在在线链路的关键路径上。

### 8.2 数据层工程设计

> 数据层对应监测层（Chapter 4），包含公共数据中心和私有数据中心两个独立部署的服务集群。

#### 8.2.1 Ingestor 服务

每个数据中心部署独立的 Ingestor 集群，职责包括：

1. **连接管理**：维护到各交易所的 WS 长连接池和 REST 轮询调度器
2. **Schema 校验**：对每条原始响应做字段完整性和类型校验，异常数据触发 S-020
3. **标准化转换**：将各交易所的异构 API 响应统一为内部标准 Schema（exchange-agnostic）
4. **新鲜度标记**：为每条数据附加 `received_at`、`exchange_ts`、`freshness_level`
5. **发布**：标准化数据写入 Kafka Topic + Redis 最新状态 + ClickHouse 归档

**公共 Ingestor 实例拓扑**：按 exchange 维度水平扩展，每个交易所 1~N 个实例（按 symbol 分片）。

**私有 Ingestor 实例拓扑**：按 account 维度水平扩展，每个账户的 WS + REST 由同一实例负责，确保该账户的数据一致性。

#### 8.2.2 频控与限流管理

> 私有数据中心的 REST 轮询与风控系统自身的控制动作共享同一个 API Key 的频控预算。

- **全局 Weight 追踪**：每个 API Key 的 Weight 使用情况实时写入 Redis（IND-S-006），Ingestor 和 Rule Engine 都读取此值。
- **动态调速**：当 Weight 使用率 > 80% 时，Ingestor 自动延长 REST 轮询间隔（优先降级低优先级数据如 ledger、exchange_info）。
- **配额保命模式**：当 > 90% 时，Ingestor 暂停所有非关键 REST 轮询，仅保留 position + balance + margin 最低频率查询。
- **Rule Engine 配额预留**：紧急控制动作（Key 吊销、撤单）所需的 API 调用有独立的 Weight 预留池（默认 10%）。

### 8.3 指标层工程设计

> 指标引擎是三级管道的核心计算层，负责将原始数据转化为 85 个标准化指标（含 6 个 signal 类型）。

#### 8.3.1 指标计算时间分层

指标按更新频率分为五个时间层级（T0~T4），每个层级对应不同的计算触发机制：

| 时间层 | 触发机制 | 典型延迟 | 指标数量 | 计算方式 | 示例 |
|--------|---------|---------|---------|---------|------|
| **T0** | Kafka 事件驱动 | <100ms | ~10 | 收到原始数据即计算 | IND-S-001 WS 连接状态 |
| **T1** | 秒级定时器 | 1~10s | ~25 | 定时从 Redis 读最新原始值计算 | IND-L-001 MMR, IND-E-001 净 Delta |
| **T2** | 滚动窗口 | 30s~5min | ~20 | 基于时间窗口内的聚合值计算 | IND-B-003 OTR, IND-M-001 价格跳变 |
| **T3** | 定时巡检 | 5min~1h | ~12 | 周期性全量扫描 | IND-P-001 提币权限, IND-S-010 可交易状态 |
| **T4** | 批处理/对账 | 1h~T+1 | ~8 | 离线批量计算 | IND-E-009 对账差异 |

**指标引擎内部线程/协程模型**：

```
┌─────────────────────────────────────────────────┐
│  Indicator Engine                                │
│                                                  │

│  └──────────────────────────────────────────┘    │

#### 8.3.2 指标存储与访问模式

| 存储 | 写入内容 | 读取方 | 保留策略 |
|------|---------|--------|---------|
| **Redis** | 每个指标的最新值（`ind:{id}:{grain}`） | Rule Engine（主要）, API（Dashboard） | 仅最新值，TTL=指标刷新周期×3 |
| **Redis** | 滑动窗口中间状态（Sorted Set） | Indicator Engine 自身（T2 计算） | 窗口长度 + 缓冲 |
| **ClickHouse** | 指标时序归档（indicator_id, ts, value, grain） | 演进层（回测）, Dashboard（趋势图） | 永久保留 |
| **Kafka** | 指标变更事件（indicator_id, new_value, ts） | Rule Engine T0/F0（事件驱动规则） | 7 天 |

#### 8.3.3 衍生指标计算链

> 部分 L2/L3 指标依赖其他指标的输出（见指标库 §0.4）。指标引擎必须保证依赖链的计算顺序。

| 衍生指标 | 上游指标 | 计算顺序保证方式 |
|----------|---------|-----------------|
| IND-E-004 总绝对敞口 | IND-E-002 | T1 计算时先算 E-002，再算 E-004 |
| IND-E-007a 预算消耗速率 | IND-E-007 | 同上 |
| IND-S-004 系统失明标志 | IND-S-001/001a/001b/002/002a/002b/003 | T0 事件驱动，任一上游变化触发重算 |

### 8.4 规则层工程设计

> 规则引擎是三级管道的最终判定层，负责基于指标值执行 82 条规则（MVP 72 + Deferred 10），产出 RiskEvent。

#### 8.4.1 规则评估时间分层

规则按评估频率分为五个层级（F0~F4），与指标的时间层级对齐但独立调度：

| 评估层 | 触发机制 | 典型延迟 | 规则数 | 说明 |
|--------|---------|---------|--------|------|
| **F0** | 指标变更事件（Kafka） | <500ms | ~8 | 事件驱动：指标变化即评估 |
| **F1** | 高频定时器 | 1~5s | ~15 | 清算/敞口等高危规则 |
| **F2** | 中频定时器 | 30s~5min | ~25 | 行为/合规/权限规则 |
| **F3** | 低频定时器 | 5min~1h | ~15 | 趋势/基线偏移检测 |
| **F4** | 批处理 cron | 1h~T+1 | ~8 | 对账/统计/报告 |

#### 8.4.3 规则配置热更新

- 规则引擎定时（30s）从 MySQL 拉取最新规则配置和治理模型
- 配置变更写入 Kafka `system.config_change` topic，规则引擎可选择事件驱动刷新
- 支持不停机更新规则参数（阈值、启用状态、冷却时间等）
- 规则逻辑变更（新增规则类型）需要代码发版

#### 8.9.2 六项关键性能风险与应对设计

尽管吞吐量不是问题，以下 6 项设计层面的风险必须在工程实现中提前处理：

**风险 1：衍生指标的依赖链计算顺序**

问题：L2/L3 衍生指标依赖其他指标的输出（如 IND-E-004 依赖 IND-E-002，IND-S-004 依赖 7 个上游指标）。T1 Ticker 如果并发计算所有指标，衍生指标可能读到上一轮的旧值。

应对：T1/T2 Ticker 内部分两个 phase 串行执行：
```
Phase 1: 计算所有 L0/L1 指标 → 写入 Redis
Phase 2: 计算所有 L2/L3 衍生指标 → 从 Redis 读最新上游值 → 写入 Redis
```
T0 事件驱动型衍生指标（如 S-004）则通过**上游指标变更事件触发重算**——任一上游指标写入 Redis 后发 Kafka 事件，S-004 的 T0 Worker 消费该事件后重算。

**风险 2：极端行情下的 WS 消息洪峰**

问题：插针/崩盘场景下 Orderbook 更新可达 100+ msg/s/symbol，20 symbols 就是 2000+ msg/s 仅 orderbook 一项。T0 Worker 可能积压。

应对：
- **消息合并**：T0 Worker 对同一 `{indicator_id}:{grain}` 做 coalescing——积压时只保留最新一条，丢弃中间态。对于风控场景，关注的是最新状态而非每一个中间状态。
- **背压机制**：当 Kafka consumer lag > 阈值（如 1000 msg）时，T0 Worker 切换为 "skip-to-latest" 模式，跳过中间消息直接消费最新 offset。
- **优先级队列**：公共行情 topic 和私有账户 topic 使用不同的 consumer group，私有数据（关乎仓位/清算）优先级高于公共行情。

**风险 3：规则实体展开膨胀与配置解析开销**

问题：71 条规则 × 四层治理继承解析 × N 个实体 = 大量"有效规则实例"。如果每次评估都从 MySQL 加载规则 + 四层继承合并，延迟和数据库压力不可接受。

应对：
- **规则配置预编译缓存**：规则引擎启动时一次性加载所有规则配置，按四层治理模型预解析为每个 `{account, strategy}` 的最终生效参数集，缓存在内存中。
- **增量更新**：MySQL 配置变更通过 Kafka `system.config_change` 事件通知规则引擎，仅重新编译受影响的规则实例，无需全量重载。
- **预计内存占用**：71 规则 × 50 实体 × ~500 bytes/实例 ≈ 1.7MB，可忽略。

**风险 4：Redis 滑动窗口内存泄漏**

问题：T2 层 20 个指标 × 50 个实体 = 1000 个 Redis Sorted Set。如果窗口 5 分钟、每秒写一个数据点，每个 Set 300 个 member。总共 ~30MB 尚可，但如果 TTL 未设或实体不再活跃，会持续泄漏。

应对：
- **Sorted Set 成员 TTL**：每次写入后，用 `ZREMRANGEBYSCORE` 清理窗口外的旧数据。
- **实体级 TTL**：对整个 Sorted Set key 设置 TTL = 窗口长度 × 3。如果该实体（如某个停止交易的 symbol）不再产生数据，key 会自动过期。
- **定时清理巡检**：T3 巡检周期内扫描 Redis 中所有 `window:*` key，清理不再活跃的实体。

**风险 5：F0/T0 端到端延迟不可控**

问题：WS 消息 → T0 指标 → F0 规则 → RiskEvent 整条链路目标 < 500ms。正常情况下每跳 ~10ms，总计 ~40ms。但 Kafka consumer lag 一旦积压，延迟就不可控。

应对：
- **独立 consumer group**：T0 和 F0 各使用独立的 Kafka consumer group，不与 T2/T3/F2/F3 共享。
- **consumer lag 监控**：Watchdog 每 5s 检查 T0/F0 consumer group 的 lag，lag > 100 即触发 S-class 系统告警。
- **旁路快通道（可选进阶）**：对最高优先级的指标（如 IND-L-001 MMR、IND-S-001 WS 状态），Ingestor 直接写 Redis 不经 Kafka，指标引擎通过 Redis keyspace notification 触发 T0 计算，跳过 Kafka 一跳。

**风险 6：多交易所扩展后的 WS 连接数限制**

问题：交易所对单 IP 的 WS 连接数有限制（如 Binance 单 IP 最多 300 条 WS 连接）。扩展到 5 交易所 × 100 symbols 后，连接数可能超限。

应对：
- **连接复用**：单条 WS 连接订阅多个 symbol 的多个 stream（Binance combined stream 支持单连接最多 200 个订阅）。
- **连接池管理**：Ingestor 维护连接池，按交易所的连接数限制动态分配。每个连接的订阅数接近上限时创建新连接。
- **多 IP 部署**：当单 IP 连接数不够时，Ingestor 部署多实例绑定不同出口 IP。

#### 8.9.3 水平扩展设计（Docker 多节点扩容）

> 性能问题的首选解决方式是**通过增加 Docker 节点水平扩展**，而非依赖代码层面的极限优化。本节明确每个服务的分片策略、扩展约束和协调机制。

**扩展能力总表**：

| 服务 | 扩展方式 | 分片键 | 实例间协调 | 扩展难度 |
|------|---------|--------|-----------|---------|
| 公共 Ingestor | ✅ 无状态水平扩展 | `exchange + symbol_range` | 分片注册表（Redis/Consul） | 低 |
| 私有 Ingestor | ✅ 无状态水平扩展 | `account` | 分片注册表 | 低 |
| 指标引擎 | ✅ 按 Kafka partition 扩展 | `indicator_category` 或 `entity_grain` | Redis 作为共享状态层 | 中 |
| 规则引擎 | ✅ 按 Kafka partition 扩展 | `rule_category` 或 `account` | Redis 作为共享指标层 + 仲裁聚合 | 中 |
| 告警服务 | ✅ 无状态 | — | Redis 告警去重 | 低 |
| 配置 API | ✅ 无状态 | — | MySQL 为单一源 | 低 |
| Watchdog | ❌ 单实例 | — | — | — |

**（1）Ingestor 水平扩展（最简单）**

公共/私有 Ingestor 是最适合加节点扩展的服务，因为每个实例负责独立的数据源子集，彼此无数据依赖。

```
扩展方式：分片注册表

┌────────────────────────────────────────────┐
│  Redis: ingestor_shard_registry            │
│                                            │
│  public:binance:BTC-USDT → ingestor-pub-1  │
│  public:binance:ETH-USDT → ingestor-pub-1  │
│  public:okx:BTC-USDT     → ingestor-pub-2  │
│  public:okx:ETH-USDT     → ingestor-pub-2  │
│                                            │
│  private:acct-001 → ingestor-priv-1        │
│  private:acct-002 → ingestor-priv-1        │
│  private:acct-003 → ingestor-priv-2        │
└────────────────────────────────────────────┘
```

- 每个实例启动时从注册表领取自己负责的 shard（或由 orchestrator 分配）
- **防重复订阅**：同一个 `exchange+symbol`（公共）或 `account`（私有）在任何时刻只能被一个实例负责
- **故障转移**：实例异常退出时，其 shard 的心跳 TTL 过期，其他实例自动接管
- **新增节点**：启动新 Docker 容器 → 自动从负载最高的实例分走部分 shard → 无需停机

**约束**：私有 Ingestor 同一 account 的 WS 和 REST 必须在同一实例内，确保该 account 数据的时序一致性。

**（2）指标引擎水平扩展**

指标引擎扩展的核心问题是：**多实例如何划分计算职责，且保证衍生指标能读到最新的上游值**。

**方案 A：按 Kafka partition 扩展（推荐）**

Kafka topic 的 partition key 按 `entity_grain`（如 `binance:BTC-USDT:acct001`）分区。多个指标引擎实例组成同一个 consumer group，每个实例自动分到不同 partition，即不同实体子集。

```
指标引擎实例-1：负责 binance 的所有实体
指标引擎实例-2：负责 okx 的所有实体
```

- 同一实体的所有指标在同一实例内计算 → 衍生指标依赖链天然在同一实例内，无需跨实例协调
- **但**：跨实体的衍生指标（如 IND-E-004 总绝对敞口需要聚合多个 account 的 E-002）需要从 Redis 读其他实例计算的值
- Redis 作为共享状态层保证最终一致性，聚合类指标允许 1~2s 的数据延迟

**方案 B：按指标类别分片**

```
指标引擎实例-1：计算 L-清算 + E-敞口 类指标（数据源：私有 DC）
指标引擎实例-2：计算 S-系统 + M-市场 类指标（数据源：公共 DC + 系统内部）
指标引擎实例-3：计算 B-行为 + P-权限 + C-合规 类指标（数据源：私有 DC）
```

- 每个实例只订阅自己需要的 Kafka topic → 更精细的资源隔离
- **但**：跨类别的衍生指标（如 IND-L-004 需要 Position + 公共 OI）需要读多个类别的数据
- 适合规模较大、需要精细调优时使用

**（3）规则引擎水平扩展**

规则引擎扩展的核心问题是：**仲裁逻辑需要看到全局事件，但评估可以分片并行**。

```
┌─────────────────────────────────────────────────────┐
│  规则引擎集群                                        │
│                                                     │
│  ┌──────────────┐  ┌──────────────┐                 │
│  │ 规则实例-1    │  │ 规则实例-2    │  ...            │
│  │ L/E/S 类规则  │  │ B/P/C/M 类   │                 │
│  │ (高优先级)    │  │ (中低优先级)   │                 │
│  └──────┬───────┘  └──────┬───────┘                 │
│         │                  │                         │
│         ▼                  ▼                         │
│  ┌─────────────────────────────────┐                │
│  │  Kafka: risk.events.raw topic   │                │
│  └──────────────┬──────────────────┘                │
│                 │                                    │
│                 ▼                                    │
│  ┌─────────────────────────────────┐                │
│  │  仲裁服务（Arbiter）             │                │
│  │  - 消费所有 raw events           │                │
│  │  - 优先级排序（5.3.1）           │                │
│  │  - 冲突检测与解决                │                │
│  │  - 输出最终 RiskEvent            │                │
│  └─────────────────────────────────┘                │
└─────────────────────────────────────────────────────┘
```

**关键设计**：将规则引擎拆为两层——
1. **评估层**（可水平扩展）：每个实例负责一部分规则的评估，产出"原始风险事件"到 `risk.events.raw` topic
2. **仲裁层**（单实例或主备）：消费所有原始事件，执行全局仲裁（优先级排序、冲突解决、cooldown 去重），输出最终 RiskEvent

评估层按规则优先级分片：高危规则（L/E/S）放在独立实例上，确保清算/系统失明等关键规则的计算不被大量低优先级规则影响。

**（4）扩展触发条件与操作手册**

| 扩展场景 | 监控指标 | 触发阈值 | 操作 |
|----------|---------|---------|------|
| 公共数据量增长 | Kafka `public.*` produce rate | > 5000 msg/s | `docker-compose scale ingestor-public=N` |
| 账户数增长 | 私有 Ingestor 的 account 数 | > 20 accounts/instance | `docker-compose scale ingestor-private=N` |
| 指标计算延迟 | T1 单轮耗时 | > 500ms | 增加指标引擎实例，调整 Kafka partition 数 |
| 规则评估延迟 | F1 单轮耗时 | > 3s | 增加规则评估实例 |
| Kafka consumer lag | T0/F0 consumer lag | > 100 msg | 增加 partition + 增加 consumer 实例 |
| Redis 压力 | Redis ops/s 或内存 | > 50K ops 或 > 10GB | 升级到 Redis Cluster |

**MVP 阶段**：所有服务单实例，但代码中必须预埋分片能力（Kafka partition key 设计、Redis key 命名空间、分片注册表接口）。这样在需要扩展时只需加容器 + 改配置，无需改代码。

### 8.10 健康治理子系统工程设计（V3.0 新增）

> 本小节对应独立设计文档 `system_health_score_design.md`（V3.0）。健康治理子系统解决的核心问题是：**风控系统自身是否健康？**——将系统的自我观测能力从离散的 S-Class 规则升级为一个统一的、可量化的、有状态机的治理子系统。

#### 8.10.1 子系统定位

健康治理子系统是叠加在三级管道之上的**内观层**（Introspection Layer），不改变现有管道架构，而是消费管道各阶段的指标来计算系统自身的健康状况。

```
┌─────────────────────────────────────────────────────────┐
│  三级管道（Data → Indicator → Rule）  — 现有架构不变     │
└──────────────────────┬──────────────────────────────────┘
                       │ 产出指标
                       ▼
┌─────────────────────────────────────────────────────────┐
│  健康治理子系统                                          │
│                                                          │
│  输入: IND-S-001~018 + IND-S-004/007/008/009             │
│  规则: S-014~S-018（5条健康治理规则）                     │
│  计算: 五维加权 → internal_health_score                   │
│  状态机: healthy ↔ internal_degraded ↔ critical           │
│           ↔ external_degraded                             │
│  输出: IND-S-017(score) + IND-S-017a(vector) + 健康报告  │
│  旁路: S-018 Canary 探针（独立验证告警投递链路完整性）    │
└─────────────────────────────────────────────────────────┘
```

#### 8.10.3 双分数模型

- **internal_health_score**（0~100 整数）：五维加权平均，代表系统内部各层的运行健康度。
- **external_dependency_summary**（结构化文本）：API 频控消耗、交易对可交易性、合约参数漂移等，不纳入数值评分，以文本摘要呈现。

**五维权重**（可配置）：

| 维度 | 默认权重 | 包含指标 |
|------|---------|---------|
| 数据采集层 | 25% | IND-S-001, 001a, 001b, 002, 002a, 002b, 003, S-014(数据侧) |
| 指标产出层 | 25% | IND-S-016(静默), 指标覆盖率, 计算延迟 |
| 规则执行层 | 20% | 规则执行延迟, 评估覆盖率, 误触发率 |
| 告警投递层 | 15% | Telegram 投递延迟, IND-S-018 Canary, 去重有效率 |
| 基础设施层 | 15% | IND-S-014(Kafka lag), IND-S-015~015d |

#### 8.10.4 Hard Cap 机制

加权平均后，应用 `min(weighted_score, applicable_caps)`，防止"其余维度正常掩盖致命缺陷"：

| 条件 | Hard Cap | 理由 |
|------|---------|------|
| S-004 数据盲区触发 | ≤40 | 风控系统失明 |
| S-009 Watchdog 失联 | ≤30 | 最后防线失效 |
| S-018 Canary 连续失败 | ≤40 | 告警链路可能断裂 |
| 任何 T0/F0 指标 lag≥1000ms | ≤50 | 实时链路延迟不可接受 |
| 多指标同时静默 (≥3) | ≤50 | 批量失效风险 |

#### 8.10.5 运行态状态机

```
         score≥80 且无外部异常
              ┌──────────┐
              │ healthy  │
              └────┬─────┘
     score<80 │         │ 外部异常
              ▼         ▼
  ┌──────────────┐  ┌───────────────────┐
  │ internal_    │  │ external_         │
  │ degraded     │  │ degraded          │
  └──────┬───────┘  └─────────┬─────────┘
         │ score<50           │ + 内部也<80
         ▼                    ▼
         ┌──────────────────────┐
         │      critical        │
         └──────────────────────┘
```

状态切换触发 S-017 告警（L1/L2/L3 按严重程度递增）+ 即时健康报告。

#### 8.10.6 Canary 探针（S-018）

独立于主链路的端到端验证：每 15 分钟向 Telegram 发送测试消息，通过 `getUpdates` API 验证消息往返。连续 2 次失败触发 L2 告警，3 次触发 L3。

**工程要点**：
- 使用独立 Telegram Bot Token，与业务告警 Bot 分离
- 不经过主链路的 Kafka → Notifier 路径，直接调用 Telegram API
- 结果写入 IND-S-018 供 S-017 健康度评分消费

### 8.11 风控控制台架构（V3.0 新增）

> 本小节对应独立设计文档 `dashboard_design.md`（V1.0）。风控控制台不是"监控看板"，而是**分层治理、按对象生效、按角色受限、支持审批发布**的风控管理平台。

#### 8.11.1 产品定位与三层能力

| 能力层 | 面向角色 | 核心能力 |
|--------|----------|----------|
| **观察层** | 值班、管理层、只读 | 系统健康度、告警态势、风险对象状态 |
| **配置层** | 管理员、交易员 | 指标运行参数、规则阈值/动作/生效范围、继承覆盖 |
| **治理层** | 超级管理员 | 角色权限、配置审批与发布、变更审计、回滚 |

#### 8.11.2 信息架构（8 个一级页面）

| 页面 | 核心功能 | 复杂度 |
|------|---------|--------|
| 总览 Home | 健康度卡片 + 告警统计 + 链路状态 + 高风险对象 | 中 |
| 健康度 Health | 五维分解 + 健康规则状态 + 容量瓶颈 + 健康报告 | 高 |
| 告警中心 Alerts | 事件列表 + 筛选 + 处置流程 | 中 |
| 对象管理 Objects | 四层治理树 + 对象详情(生效规则/指标/告警/变更) | 高 |
| 指标库 Indicators | 指标目录 + 运行态 + 配置 + 依赖图 | 中 |
| 规则库 Rules | 规则模板 + 规则视图 + 对象视图 + 差异视图 | 最高 |
| 变更中心 Changes | 双轨发布(Draft→Preview→Approval→Publish) + 审计 + 回滚 | 高 |
| 权限管理 Access | 用户管理 + RBAC + Scope 绑定 + 权限矩阵 | 中 |

#### 8.11.3 RBAC + Scope 权限模型

**4 种角色**：

| 角色 | 代号 | 定位 |
|------|------|------|
| SuperAdmin | SA | 平台最高管理员，全局权限 |
| Admin | ADM | 风控管理员/项目负责人，可被限定到特定 Project |
| Trader | TRD | 交易员/策略运营，可被限定到特定 Team/Strategy |
| Viewer | VW | 只读观察员/值班 |

**Scope 绑定**：每个用户除角色外，还绑定 scope（global / project / team / strategy / account），实现细粒度访问控制。所有 API 请求经 scope 中间件过滤，非 global-SuperAdmin 的查询自动注入 `WHERE scope_id IN (...)` 条件。

**关键权限矩阵**：

| 操作 | SA | ADM | TRD | VW |
|------|-----|------|------|-----|
| 修改规则模板 | ✅ | ❌ | ❌ | ❌ |
| 创建/修改规则绑定 | ✅ | ✅(scope内) | ✅(scope内,低风险) | ❌ |
| 审批高风险变更 | ✅ | ❌ | ❌ | ❌ |
| 审批中风险变更 | ✅ | ✅ | ❌ | ❌ |
| 回滚配置 | ✅ | ❌ | ❌ | ❌ |
| 管理用户/角色 | ✅ | ❌ | ❌ | ❌ |

#### 8.11.4 规则配置数据模型

规则配置采用**模板 + 绑定**分离架构，对齐已有 `rule_bindings` 表（database-schema.md §2.3）：

- **Rule Template**（`risk_rules` 表）：平台维护的标准定义，含默认阈值/动作/时间策略
- **Rule Binding**（`rule_bindings` 表）：scope 级参数覆盖，支持三种操作：
  - **继承**：不做配置，沿用上层
  - **覆盖**：只改部分参数，其余继承（JSON config 部分 merge）
  - **显式关闭**：`enabled=false`，即使上层启用也不检测

生效解析算法：`Account > Strategy > Team > Project > Global`，逐层 merge，就近生效。

#### 8.11.5 双轨配置发布

高风险配置变更不能直接生效，必须走审批流：

```
草稿 Draft → 预览 Preview (影响分析) → 审批 Approval → 发布 Publish
                                                        ↓
                                                    回滚 Rollback
```

| 风险等级 | 触发条件 | 发布要求 |
|----------|---------|---------|
| 🟢 低 | cooldown 微调等 | Trader 可直接发布 |
| 🟡 中 | 关键规则阈值变更 | Admin 审批后发布 |
| 🔴 高 | L/S/P0/P1 规则变更、全局修改 | SuperAdmin 审批后发布 |

## 10. 组织治理与防内鬼机制

> 系统再完善，如果最高权限的人可以静默关闭风控、篡改审计日志，则一切归零。本节独立于五层方法论之外，是"治理方法论之上的治理"。

为防止最高权限的滥用或内鬼操作，系统管理机制必须遵循：

- **双人授权（Four-Eyes Principle）**：任何风险预算调高、关键告警规则静默、Key 权限扩大的操作，必须经双人审批或走审批流，禁止单人一键修改。
- **带外审计（Out-of-band Audit Log）**：高危配置变更日志必须实时发往隔离的存储（如独立云桶或安全系统），防止被拥有 DB 权限的内部人员抹除。
