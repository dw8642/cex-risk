# 风控规则库审阅汇总（从 L-001 开始）

> 本文档用于汇总此前对 `rule_library_v3.0_checklist.md` 的逐条审阅结论。  
> 范围覆盖：L / E / S / M / B / C / P / BASE。  
> 当前不包含 9. 三级策略专属规则的完整人工审阅结论，9.* 后续单独补充。

---

# 1. 审阅基线与统一原则

## 1.1 当前审阅基线

- 当前语义基线以 **Binance U 本位合约** 为主。
- **暂不纳入币本位合约**。
- 风控系统与交易系统保持职责隔离：
  - 风控优先做 **观测、判定、告警**
  - 自动交易动作属于后续能力，不在当前版本强依赖
- REST 仍视为关键真相源之一。
- 数据链路判定中，必须区分：
  - 链路是否活着
  - 数据是否新鲜
  - 数据是否可信

## 1.2 统一审阅方法

每条规则主要按以下维度审：

1. 业务目标是否成立
2. 指标类型是否合理
3. 风险对象和适用范围是否准确
4. 规则条件是否具备可执行性
5. 阈值是否可配置且有分层空间
6. 告警等级和恢复条件是否合理
7. 是否属于 MVP 可落地规则，还是研究型规则

## 1.3 全局共性结论

本轮审阅中，多数规则都出现了以下共性优化方向：

- 补充 **账户适用**（现货 / 合约 / 组合型）
- 将抽象描述改为 **结构化条件**
- 明确 **前置条件**，减少误报
- 明确 **阈值分层维度**（交易所 / 市场 / 策略类型 / 账户）
- 补充 **恢复条件**
- 对研究型规则明确标识，不强行假装成熟

# 2. L-清算与生存类审阅汇总

## L-001 维持保证金率过高

- **结论**：必须保留。
- **核心判断**：在 Binance Futures 语义下，`maintMarginRatio` 越高越危险，规则方向成立。
- **关键点**：
  - 规则名、指标名、危险方向必须严格一致
  - 不能把它写成“越低越危险”
- **优化重点**：
  - 明确采用 Binance futures 语义
  - 名称、条件、告警文案统一为“越高越危险”

## L-002 ADL 风险升高

- **结论**：应保留。
- **核心判断**：业务含义合理，属于临近被强平队列接管的重要信号。
- **关键点**：
  - 需明确按账户、仓位还是 symbol 粒度观测
  - 不同模式下阈值可能不同
- **优化重点**：
  - 明确 ADL 数据源与粒度
  - 明确 L1/L2 分层条件

## L-003 距离强平价过近

- **结论**：必须保留。
- **核心判断**：这是比 L-001 更直观的生存边界规则。
- **关键点**：
  - 需要统一距离定义：相对价格距离 / 美元距离 / 百分比
  - 需考虑多空方向符号统一
- **优化重点**：
  - 统一 `distance_to_liq_pct`
  - 补充多空统一口径

## L-004 净仓方向暴露下的清算风险放大

- **结论**：必须保留。
- **核心判断**：规则方向对，但必须严格区分单向模式和双向持仓模式。
- **关键点**：
  - 单向持仓：看净仓即可
  - 双向持仓：long / short 必须分开看
- **优化重点**：
  - 明确 one-way vs hedge mode 判定逻辑
  - 避免净仓掩盖真实单边风险

## L-005 生存边际过薄

- **结论**：应保留，但当前更偏概念规则。
- **核心判断**：业务目标对，但短期不够量化。
- **关键点**：
  - 它是一个综合性规则，不适合现在假装成简单数值阈值规则
- **优化重点**：
  - 保留为研究型 / 组合型规则
  - 后续由多个已量化规则联动支持

# 3. E-敞口与对账类审阅汇总

## E-001 单市场敞口过高

- **结论**：必须保留。
- **范围基线**：现货 + U 本位合约，暂不含币本位。
- **优化重点**：明确市场口径、折算币种、按市场类型分层阈值。

## E-002 单市场集中度过高

- **结论**：应保留。
- **核心判断**：更像“单市场绝对敞口上限”，不完全是统计学意义上的集中度。
- **优化重点**：避免名称和实际条件错位。

## E-003 对冲失配 / 未对冲敞口

- **结论**：必须保留。
- **核心判断**：前提是先定义 hedge mapping。
- **优化重点**：明确哪些腿构成对冲对、按什么键关联。

## E-004 总绝对敞口过高

- **结论**：必须保留。
- **核心判断**：典型账户级总风险边界。
- **优化重点**：按账户组 / 项目 / 市场层分级。

## E-005 账户组总绝对敞口过高

- **结论**：必须保留。
- **核心判断**：是 E-004 的治理升级版。
- **优化重点**：先统一账户组 / team / project 口径。

## E-006 仓位变化速度异常

- **结论**：必须保留。
- **核心判断**：业务价值高，但必须明确定义“变化速度”。
- **优化重点**：
  - 明确时间窗口
  - 明确用名义价值还是数量
  - 考虑双向持仓模式

## E-007 账户权益/保证金缓冲不足

- **结论**：必须保留。
- **核心判断**：现货和合约语义不同，不能混写。
- **优化重点**：
  - 现货看可用资产缓冲
  - 合约看权益/保证金缓冲

## E-008 风险预算接近耗尽

- **结论**：必须保留。
- **核心判断**：依赖风险预算模型。
- **优化重点**：先定义预算对象与预算消耗口径。

## E-009 风险预算已突破

- **结论**：必须保留。
- **核心判断**：是 E-008 的硬边界版本，严重度应更高。
- **优化重点**：与 E-008 做出“接近耗尽 vs 已突破”的明确边界。

## E-010 资金费率损耗异常

- **结论**：应保留。
- **核心判断**：当前更接近“资金费成本异常”，不是严格的波动规则。
- **优化重点**：明确窗口、累计口径、收益影响口径。

## E-011 外部对账差异超限

- **结论**：必须保留。
- **核心判断**：应依赖外部账户系统结果，不在风控内重造对账系统。
- **优化重点**：
  - 使用 `abs(reconciliation_diff)`
  - 恢复条件按对账周期计算

## E-012 风险预算消耗速度过快

- **结论**：必须保留。
- **核心判断**：是 E-008 / E-009 的前置信号。
- **优化重点**：定义 burn rate 窗口与预算映射方式。

# 4. S-系统与接入类审阅汇总

## S-001 公共数据订阅断联/延迟

- **结论**：必须保留，而且非常关键。
- **核心判断**：不能只看连接层，必须同时看业务数据鲜活度。
- **优化重点**：
  - 三层监控：连接层 / 数据类型层 / 核心 symbol 层
  - 全量观测，分层告警

## S-002 风控系统整体失明风险

- **结论**：必须保留。
- **核心判断**：这是 S-001 / S-004 / S-005 的元规则。
- **优化重点**：
  - 用关键源健康状态聚合判断
  - 直接走 L3 合理

## S-003 API 频控耗尽风险

- **结论**：必须保留，但必须收窄语义。
- **核心判断**：当前只能监控风控自己的只读 API 配额，不能越界假设能看见交易系统的交易 API 配额。
- **优化重点**：
  - 明确是“风控只读 API 频控使用率”
  - 保持风控与交易分离架构

## S-004 私有数据订阅断联/延迟

- **结论**：必须保留，而且比 S-001 更危险。
- **核心判断**：需区分空闲账户无事件与真实异常。
- **优化重点**：
  - 连接层 + 业务层双层判定
  - 引入 REST 回退决定严重度

## S-005 数据陈旧/快照过期检测

- **结论**：必须保留。
- **核心判断**：解决“连接活着但数据已不可信”的静默故障。
- **优化重点**：
  - 区分事件流与快照型数据源
  - 分别定义 freshness 阈值

## S-006 多源数据不一致

- **结论**：应保留，但当前偏研究型。
- **核心判断**：不应只做一个总分，要拆维度比较。
- **优化重点**：逐项比较价格、余额、仓位、订单状态等。

## S-007 指标/数据管道延迟

- **结论**：必须保留。
- **核心判断**：这是链路健康的重要补充。
- **优化重点**：明确延迟发生在哪一段链路。

## S-008 规则引擎异常

- **结论**：必须保留。
- **核心判断**：要拆成具体子条件，不能只写“引擎异常”。
- **优化重点**：队列积压、消费停滞、规则执行超时等。

## S-009 Watchdog/巡检链路失效

- **结论**：必须保留。
- **核心判断**：是端到端健康检查的重要兜底。
- **优化重点**：明确 watchdog 成功标准和超时标准。

## S-010 交易所临时不可交易

- **结论**：必须保留。
- **核心判断**：这是外部环境状态的重要输入。
- **优化重点**：结合 API 状态、公告、探测结果三类信号。

## S-011 分组控制链路失效

- **结论**：保留，但当前偏 TBD。
- **核心判断**：依赖未来分组控制能力成熟。
- **优化重点**：先确认控制面能力边界。

## S-012 批量异常来自同源

- **结论**：保留，但当前偏 TBD。
- **核心判断**：必须先定义“同源”和“同批”。
- **优化重点**：明确 source dimension 与批量窗口定义。

## S-013 API Schema / 接口语义漂移

- **结论**：必须保留。
- **核心判断**：这是实际系统非常真实的风险。
- **优化重点**：版本、字段缺失、字段语义变化都要监控。

# 5. M-市场与微观结构类审阅汇总

## M-001 波动率突升

- **结论**：必须保留。
- **核心判断**：MVP 先做价格跳变，后续再补真实波动率。
- **优化重点**：避免“价格跳变”和“波动率”概念混在一起。

## M-002 交易所接口健康恶化

- **结论**：必须保留。
- **核心判断**：它更像市场可达性 / 交易所系统状态规则。
- **优化重点**：按公共接口、私有接口、交易接口分层。

## M-003 极端市场参与度控制触发

- **结论**：应保留。
- **核心判断**：更偏控制联动规则，不只是单纯检测规则。
- **优化重点**：与 M-001 / M-002 联动。

## M-004 资金费率异常

- **结论**：应保留。
- **核心判断**：当前更像“资金费率水平异常”，不是“波动率异常”。
- **优化重点**：修正规则名或补全真实波动定义。

## M-005 深度不足

- **结论**：必须保留。
- **核心判断**：非常实用，但必须明确定义深度口径。
- **优化重点**：
  - 看几档
  - 看名义金额还是数量
  - 买卖侧是否分开

## M-006 买卖价差异常扩大

- **结论**：必须保留。
- **核心判断**：成熟且直接。
- **优化重点**：按 symbol / 市场类型分层阈值。

## M-007 跨市场价差异常

- **结论**：必须保留。
- **核心判断**：前提是统一 instrument mapping。
- **优化重点**：严格保证比较对象一致。

## M-008 有毒流量 / 恶劣对手盘嫌疑

- **结论**：保留，但当前属研究型。
- **核心判断**：短期不适合作为成熟规则。
- **优化重点**：依赖更高级微观结构特征。

## M-009 综合市场异常状态

- **结论**：保留。
- **核心判断**：依赖 M-005 / M-006 / M-008 等成熟度。
- **优化重点**：作为组合型上层规则，不宜过早独立落地。

# 6. B-行为类审阅汇总

## B-001 异常成交放量

- **结论**：必须保留。
- **核心判断**：不能只看绝对量，必须结合策略基线。
- **优化重点**：相对基线 + 绝对上限双重判断。

## B-002 单边成交比例异常

- **结论**：必须保留。
- **核心判断**：要有最小成交量门槛，否则误报高。
- **优化重点**：统一方向比例定义。

## B-003 单笔订单规模异常

- **结论**：必须保留。
- **核心判断**：它是 BASE-002 的事后告警版。
- **优化重点**：明确与 BASE-002 的分工边界。

## B-004 非授权交易

- **结论**：必须保留，而且很重要。
- **核心判断**：不是在看量，而是在看行为是否被允许。
- **优化重点**：
  - 补充账户适用：现货 + 合约
  - 条件写成白名单不匹配
  - 明确授权层级与继承逻辑
  - 明确“方向”的语义

## B-005 高成交低净仓变化

- **结论**：应保留，但误报风险高。
- **核心判断**：可用于发现刷量 / 对敲嫌疑，但必须强依赖策略上下文。
- **优化重点**：
  - 增加最小成交量门槛
  - 用 USD 统一净仓变化口径
  - 对做市策略做强过滤

## B-006 异常滑点 / 执行质量劣化

- **结论**：必须保留。
- **核心判断**：要拆成单笔异常和窗口持续劣化两层。
- **优化重点**：
  - 明确参考价定义
  - 统一滑点口径
  - 区分“异常滑点”与“执行质量劣化”

## B-007 手工单异常

- **结论**：必须保留。
- **核心判断**：本质是订单来源治理规则。
- **优化重点**：
  - 用订单来源 + 内部审计日志对账
  - 明确“系统单”定义
  - 做人工闭环恢复

## B-008 对敲 / 刷量嫌疑（基础版）

- **结论**：可以保留，但应视为研究型规则。
- **核心判断**：难点不在名字，而在区分正常做市和异常刷量。
- **优化重点**：
  - 保留为线索规则
  - 不要过早承诺统一 `score`

## B-009 Wash Trade / Self-Trade

- **结论**：必须保留，而且成熟度高于 B-008。
- **核心判断**：应区分同账户确认型与关联账户疑似型。
- **优化重点**：
  - 不要只用单个 bool
  - 用计数 / 比例 / 匹配特征描述

## B-010 挂撤单比例（OTR）异常

- **结论**：必须保留。
- **核心判断**：要先明确内部 OTR 公式，并加入最小活动量门槛。
- **优化重点**：
  - 分策略类型设阈值
  - 可分 L1/L2 两档

## B-011 多账户高相似执行行为

- **结论**：可以保留，但属于高级研究型规则。
- **核心判断**：先定义“相似”的维度，再谈分数。
- **优化重点**：
  - 时间、方向、价格、仓位路径拆开看
  - 仅在已知关联账户组内启用

## B-012 单腿暴露（Leg Risk）监控

- **结论**：必须保留。
- **核心判断**：多腿策略中非常真实的损失风险。
- **优化重点**：
  - 必须先定义组合关联键
  - 条件写成“未完成腿数 + 超时 + 裸露敞口”

# 7. C-平台合规类审阅汇总

## C-001 多账户关联执行合规风险

- **结论**：保留，但更适合合规审计层。
- **核心判断**：它更像 B-011 / B-009 的合规解释层，不应与行为检测层混写。
- **优化重点**：明确关联账户定义与批处理定位。

## C-002 多账户规避平台限制风险

- **结论**：保留，但偏治理 / 审计型规则。
- **核心判断**：必须先定义“规避什么限制”。
- **优化重点**：优先明确 OTR、仓位、资格、频控等规避对象。

## C-003 做市资格 / 激励资格受损

- **结论**：必须保留，而且相对成熟。
- **核心判断**：应做成“前兆态 + 结果态”双层。
- **优化重点**：资格状态 API 与项目考核指标联合使用。

## C-004 账户被平台限制 / 降权

- **结论**：必须保留。
- **核心判断**：要把限制类型拆开，不要只写一个总状态。
- **优化重点**：分类限制类型与能力退化征兆。

# 8. P-权限类审阅汇总

## P-001 提币权限异常开启

- **结论**：必须保留，是权限底线规则。
- **核心判断**：这类规则是边界判断，不需要数值阈值。
- **优化重点**：白名单升级为“审批豁免机制”。

## P-002 非授权交易范围开放

- **结论**：必须保留。
- **核心判断**：它是 B-004 的上游权限版。
- **优化重点**：先统一授权范围模型。

## P-003 高危 API Key 未及时停用

- **结论**：应保留，但偏安全治理规则。
- **核心判断**：必须先定义什么是高危 Key。
- **优化重点**：权限、轮转、IP 白名单、归属、闲置情况联合定义风险级别。

## P-004 多账户权限过度扩散风险

- **结论**：可以保留，但更适合治理审计。
- **核心判断**：不是高频实时风险，更像权限面审计。
- **优化重点**：量化扩散度。

## P-005 大额 / 异常提币实时监控

- **结论**：必须保留，而且是电话级核心规则之一。
- **核心判断**：必须拆“大额提币”和“异常提币模式”。
- **优化重点**：
  - 地址、时间、频率、新地址等模式识别
  - 人工闭环恢复

## P-006 异常资金划转监控

- **结论**：应保留。
- **核心判断**：可以从纯 TBD 推进为半结构化规则。
- **优化重点**：金额、频率、路径三类基础检测先落地。

## P-007 API Key IP 白名单变更监控

- **结论**：必须保留。
- **核心判断**：这是 API Key 边界安全的重要规则。
- **优化重点**：把变更类型拆成不同严重度。

# 9. BASE-执行基础规则库审阅汇总

## BASE-001 策略运行时间窗口检查

- **结论**：必须保留。
- **核心判断**：这是执行治理规则，不是市场风险规则。
- **优化重点**：跨日窗口、时区、自动恢复策略要说清。

## BASE-002 单笔订单规模 / 支出范围检查

- **结论**：必须保留，是 BASE 层核心规则之一。
- **核心判断**：这是事前防 fat finger 的硬边界。
- **优化重点**：同时支持数量、金额、合约张数口径。

## BASE-003 下单价格偏离限制

- **结论**：必须保留，是 BASE 层核心规则之一。
- **核心判断**：它是 B-006 的上游预防规则。
- **优化重点**：统一参考价口径与分层阈值。

## BASE-004 下单间隔与节奏检查

- **结论**：应保留。
- **核心判断**：关键不是越快越危险，而是是否偏离该策略合法节奏。
- **优化重点**：
  - 分清下单节奏与成交节奏
  - 不要用模糊 jitter 公式

## BASE-005 执行账户 / IP 分发异常检查

- **结论**：可以保留，但当前成熟度一般。
- **核心判断**：先做账户集中度，IP 维度待数据能力成熟后再做。
- **优化重点**：拆成账户分布异常和 IP 分布异常两层。
