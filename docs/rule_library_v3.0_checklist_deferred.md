## 0.1a 规则评估与告警时间策略

**设计原则：不把"指标更新时间"直接等同于"告警频率"。**

规则时间设计建议拆成 4 层：

1. **数据源刷新节奏**：WS / REST / 批处理多久产生新数据
2. **指标更新时间**：指标缓存多久刷新 / 重算一次
3. **规则评估频率**：规则引擎多久读取指标并判定一次
4. **告警冷却与恢复**：同一 `rule + entity + severity` 多久内不重复推送，以及恢复需要连续多少次正常

建议后续为每条规则统一补充以下时间字段：

| 字段 | 含义 | 说明 |
|------|------|------|
| `evaluation_tier` | 评估时间层级 | F0/F1/F2/F3/F4 |
| `evaluation_interval` | 规则评估频率 | 如 `event-driven` / `1s` / `30s` / `15min` |
| `observation_window` | 观察窗口 | 仅窗口型规则需要，如 `5min` / `1h` / `24h` |
| `window_step` | 滑动步长 | 仅窗口型规则需要，如 `30s` / `1min` |
| `cooldown_seconds` | 重复告警冷却 | 同一对象冷却期内不重复发同级告警 |
| `recover_hysteresis` | 恢复迟滞 | 连续 N 次正常才恢复，避免阈值抖动 |

### 时间层级建议

| 层级 | 含义 | 目标延迟 | 适用规则特征 |
|------|------|----------|--------------|
| F0 | 事件触发 / 硬门禁 | <500ms | 可同步拦截、动作不可逆、逐笔/逐事件判定 |
| F1 | 秒级状态 | 1~5s | 高危持续状态，风险扩散快 |
| F2 | 滚动窗口 | 30s~5min | 行为模式、节奏分析、市场窗口统计 |
| F3 | 定时巡检 | 5min~1h | 配置漂移、治理检查、慢变量 |
| F4 | 批处理 / 对账 / 审计 | 1h~资金周期/T+1 | 外部依赖、跨账户聚合、合规审计 |

### Deferred 规则时间分层建议

| 时间层 | 建议规则 |
|--------|----------|
| F0 事件触发 / 硬门禁 | LIQ-001, LIQ-003, MAN-001, ACCDIS-002 |
| F1 秒级状态 | B-012, STG-001 |
| F2 滚动窗口 | L-005, E-003, MAN-002, ACCDIS-001, ARB-002, LIQ-002 |
| F3 定时巡检 | S-006, S-011, S-012, S-013 |
| F4 批处理 / 对账 / 审计 | B-011, C-001, C-002, M-009 |

### 默认调度参数建议

| 时间层 | `evaluation_interval` | `observation_window` | `window_step` | `cooldown_seconds` | `recover_hysteresis` |
|--------|-----------------------|----------------------|---------------|--------------------|----------------------|
| F0 | `event-driven` | — | — | 60~300 | 1 次事件恢复/人工关闭 |
| F1 | `1s~5s` | `point-in-time` | — | 300~900 | 连续 2~3 次正常 |
| F2 | `30s~5min` | `5min/15min/1h/24h` | `30s/1min/5min` | 300~1800 | 连续 2 个窗口正常 |
| F3 | `5min~1h` | `point-in-time` 或 `calendar_window` | — | 1800~14400 | 连续 2 次巡检正常 |
| F4 | `1h~T+1` | `资金周期/批次窗口` | `批次触发` | 按批次 | 通常人工关闭或下批次恢复 |

> 说明：
>
> - **窗口长度 ≠ 评估频率**。例如 E-005 可用 `1h` 观察窗口，但每 `30s` 重算一次。
> - **规则评估频率 ≠ Telegram 推送频率**。推送仍需依赖 `cooldown_seconds` 去重。
> - 同一规则若严重度升级（如 L2 → L3），建议**允许越过冷却**立即再次推送。

## 1.5 L-005 联合保证金/抵押物折价双杀

- **规则编号**：L-005
- **规则名称**：联合保证金/抵押物折价双杀
- **优先级**：P1（但 MVP 阶段不开发，条件未量化 + 数据源复杂度高）
- **MVP 状态**：❌ MVP 不纳入，后续版本开发
- **规则层级**：一级：平台统一主规则库
- **来源规则**：—
- **★ 交易员收编**：否
- **指标类型**：C — 跨源衍生 (DRV)（抵押物价格 + 折扣率配置 + 账户资产，多源组合）
- **适用范围**：仅合约（联合保证金 / Portfolio Margin 模式），仅对存在非稳定币抵押物的账户生效
- **风险对象**：账户（联合保证金模式）
- **业务目的**：防止联合保证金模式下抵押物价格下跌 + 折扣率恶化的"双杀"效应，导致有效保证金急剧缩水
- **数据来源**：
  - 主判定源：账户 Asset REST API（抵押物持仓 + 账户余额）
  - 辅助源：抵押物市场价格 Feed（如 BTC/ETH 价格）
  - 辅助源：交易所折扣率配置（Binance `collateralMarginLevel` 等）
  - REST 为最终裁定
- **监控参数 / 指标**：
  - `collateral_assets[]`（各抵押物币种及数量）
  - `collateral_price[]`（各抵押物当前市场价格）
  - `haircut_rate[]`（各抵押物折扣率，交易所配置）
  - `effective_collateral_value = Σ(qty × price × (1 - haircut_rate))`（折后有效抵押物价值）
  - `total_margin_required`（当前总维持保证金需求）
  - `collateral_margin_ratio = effective_collateral_value / total_margin_required`（核心判定比率）
- **规则条件**（待量化，当前为设计方向）：
  - ⚠️ **条件尚未完成量化**，以下为设计方向，需和交易员确认具体阈值后才可进入研发
  - 静态判定：`collateral_margin_ratio <= threshold`（有效抵押物价值 / 维持保证金需求 跌破安全线）
  - 变化量辅助：非稳定币抵押物价格在 N 分钟窗口内跌幅 ≥ X%，同时 `collateral_margin_ratio` 下降 ≥ Y%（捕捉"双杀"速率）
  - 条件方向：`<=`（比率越低越危险）
- **阈值配置项**（待量化）：
  - `min_collateral_margin_ratio`（静态安全线，如 1.5x，待确认）
  - `price_drop_pct_window`（抵押物价格跌幅窗口，如 5min / 15min，待确认）
  - `price_drop_threshold`（价格跌幅阈值，如 10%，待确认）
  - `ratio_decline_threshold`（比率下降幅度阈值，待确认）
- **告警等级建议**：
  - L1：`collateral_margin_ratio` 接近安全线（预警）
  - L2：`collateral_margin_ratio` 跌破安全线 或 检测到双杀速率
- **系统动作建议**：
  - L1：Telegram-info 低频预警
  - L2：Telegram-critical 高频预警
  - [后续] 自动暂停该账户新开仓
- **恢复条件建议**：
  - `collateral_margin_ratio` 回升至安全线以上，连续 2 个窗口确认
- **告警文案参考**：
  - L1：`【预警】{exchange} {account} 联合保证金有效抵押率 {ratio}x，接近安全线 {threshold}x`
  - L2：`【严重预警】{exchange} {account} 联合保证金有效抵押率 {ratio}x 跌破安全线，非稳定币抵押物 {asset} 近{window}分钟跌幅 {drop_pct}%`
- **实现归属**：risk_platform
- **实现状态**：⏸️ MVP 不开发（条件未量化，后续版本排期）
- **后续实现路径建议**：
  - **路径 A（简化版 / 推荐先行）**：直接监控交易所已有的统一保证金率字段（如 Binance `uniMMR`），跌破阈值即告警。实现简单，指标类型可降为 A-RT
  - **路径 B（完整版 / 后续迭代）**：自行拉取抵押物明细 + 价格 + 折扣率，计算分项变化，告警文案可具体到"哪个抵押物跌了多少"。复杂度高但信息丰富
  - 建议后续版本先走路径 A 快速上线，再叠加路径 B 增强
- **评审结论**：
  - ✅ 风险定义合理，双杀场景真实存在
  - ✅ 指标类型 C-DRV 合理
  - ✅ 风险对象正确
  - ⚠️ **条件表达未完成**：当前只是风险描述，不是可执行判定逻辑
  - ⚠️ 阈值全部待确认，需交易员和实际数据支撑后才可定
  - ⚠️ 需确认交易所 API 是否能实时获取折扣率及抵押物明细
  - ❌ **MVP 不开发**：条件未量化 + 数据源复杂度高，放入后续版本
- **待确认问题**：
  - 哪些交易所支持联合保证金？各交易所 API 是否提供折扣率和抵押物明细？
  - 静态安全线（`min_collateral_margin_ratio`）初始值如何定？
  - 双杀速率判定的时间窗口和阈值如何定？
  - 是否需要区分不同抵押物币种分别判断（如 BTC 抵押 vs ETH 抵押风险不同）？
- **确认状态**：⬜确认 / ⬜删除 / ⬜暂缓 / ⬜修改 / 修改意见：______

- **来源规则**：RISK-ARB-001（含原 ARB-001 套利策略收编，ARB-001 已降为本规则的策略级参数映射）
- **★ 交易员收编**：★ 是
- **指标类型**：C — 跨源衍生 (DRV)（多账户仓位 + 对冲映射关系，跨源计算）
- **适用范围**：合约为主（支持现货 + 合约组合对冲），跨账户/跨交易所
- **风险对象**：账户组 / 套利策略组
- **业务目的**：监控套利/对冲策略的未对冲敞口，防止缺口扩大导致净风险失控
- **同族规则**：B-012（单腿暴露）— 检测同一风险的不同阶段。E-003 基于仓位快照周期检测（事后），B-012 基于 Order/Fill 实时流检测执行中腿超时（实时）
- **前置条件**（规则生效的必要条件）：
  - ⚠️ **必须已配置对冲映射关系**（hedging_pair_id / 策略元数据中定义的对冲腿）
  - 未配置映射的策略不参与本规则计算
  - 对冲映射定义至少包含：策略 ID、A 腿（账户+交易对+方向）、B 腿（账户+交易对+方向）、预期比例
- **数据来源**：
  - 主判定源：Position REST API（多账户持仓快照）
  - 辅助源：Mark Price（USD 换算）
  - 配置源：对冲映射关系表（策略元数据）
  - REST 为最终裁定

  - `hedge_pair_config`（对冲对配置：A 腿、B 腿、预期比例）
  - `leg_a_usd`（A 腿 USD 名义敞口）
  - `leg_b_usd`（B 腿 USD 名义敞口）
  - `hedge_gap_usd = abs(leg_a_usd - leg_b_usd × expected_ratio)`（按 USD 名义敞口统一换算后的未对冲缺口）
- **规则条件**：
  - `hedge_gap_usd >= threshold`
  - 条件方向：`>=`（缺口越大风险越高）
- **阈值配置项**：
  - `max_hedge_gap_usd`（待确认，按策略组级可配）
- **告警等级建议**：
  - L1：轻度缺口（预警）
  - L2：明显缺口（对冲策略成立条件受威胁）
- **系统动作建议**：
  - L1：Telegram-info 低频预警
  - L2：Telegram-critical 高频预警
  - [后续] 暂停该策略组新开仓
- **恢复条件建议**：
  - 对冲缺口缩小至阈值以下，连续 2 个窗口确认
- **告警文案参考**：
  - L1：`【预警】策略组 {strategy_group} 对冲缺口 {gap_usd} USD，超阈值 {threshold} USD`
  - L2：`【严重预警】策略组 {strategy_group} 对冲缺口 {gap_usd} USD，严重超限，对冲有效性存疑`
- **实现归属**：risk_platform（BASE 层）
- **实现状态**：⏸️ MVP 不开发（前置条件未满足 + 策略元数据体系未建）

  - ✅ 指标类型 C-DRV 合理
  - ✅ 风险对象（策略组级）合理
  - ⚠️ 降级为 BASE 层：强依赖策略上下文，不适合平台统一规则
  - ⚠️ `hedge_gap_usd` 定义需细化：USD 名义敞口统一换算、对冲比例配置
