# 风控规则库 V3.0 — 逐条审核清单

## 0. 使用说明

本文档用于和以下角色逐条确认风控规则库：

- 老板
- 交易员 / 交易负责人
- 风控负责人
- 产品经理
- 研发负责人

本清单重点回答以下问题：

1. 这条规则要不要做？
2. 为什么做？
3. 优先级是什么？
4. 数据来源是否具备？
5. 告警等级怎么分？（L1/L2/L3）
6. 触发后系统动作是什么？（MVP 阶段仅通知，后续可自动化）
7. 是否需要自动恢复？
8. 是风控平台做，还是策略引擎做？
9. 当前是否已经确认，是否可进入研发排期？

## 0.1 MVP 阶段告警能力说明

**MVP 阶段唯一告警通道：Telegram**

| 等级 | 通道 | 说明 |
|------|------|------|
| L1 | Telegram-info | 低频预警，常规风险提示 |
| L2 | Telegram-critical | 高频预警，需重点关注 |
| L3 | Telegram 语音电话 | 最高级告警，通过 Telegram 语音通话实现 |

**MVP 阶段系统动作能力边界：**

- **[MVP] 可做**：所有告警通知（L1/L2/L3 三级 Telegram 消息 + 语音）
- **[后续] 需要后续迭代**：自动化干预动作，包括：暂停策略、系统降级、限制开仓/交易、拒绝订单、标记数据不可信、强制刷新等

> 本清单中，涉及自动化干预的规则已用 **[MVP]** / **[后续]** 标记拆分。MVP 阶段这些规则仍然生效（发送告警通知），自动化动作在后续版本中逐步上线。
> 共 **17 条规则** 包含 [后续] 自动化动作，涉及类别：L(1), E(4), S(4), M(2), B(1), BASE(4), POST-MVP(1)。

**指标类型分类（按数据获取方式）：**

| 类型 | 简称 | 含义 | 数量 | MVP 实现难度 |
|------|------|------|------|-------------|
| A | RT 实时可读 | 交易所 API/WS 直接返回，一次调用即得 | 19 | ⭐ 低 |
| B | AGG 窗口聚合 | 需收集时间序列数据，做窗口聚合/累加 | 16 | ⭐⭐ 中 |
| C | DRV 跨源衍生 | 需组合多个数据源（跨账户/跨交易所）计算 | 9 | ⭐⭐⭐ 中高 |
| D | SYS 系统自观测 | 我方基础设施产生的指标，非来自交易所 | 16 | ⭐⭐ 中（需先建设） |
| E | TBD 尚未量化 | 概念清晰但缺乏明确可计算的指标定义 | 12 | ⭐⭐⭐⭐ 高 |

> 每条规则的「指标类型」字段标注在「★ 交易员收编」之后、「风险对象」之前。
> 10 条 POST-MVP 规则暂未分类。

## 1.1 L-001 ★ 维持保证金占比过高

- **规则编号**：L-001
- **规则名称**：维持保证金占比过高
- **优先级**：P0
- **规则层级**：一级：平台统一主规则库
- **来源规则**：RISK-ACC-003
- **★ 交易员收编**：★ 是
- **指标类型**：A — 实时可读 (RT)（交易所账户 API 直接返回 maintMarginRatio）
- **风险对象**：账户（合约账户）
- **业务目的**：维持保证金占比越高说明仓位所需保证金占总价值比例越大，距离强平越近。是清算防线第一道。
- **数据来源**：
  - **主判定源**：交易所账户 REST 接口（`maintMarginRatio` 字段）
  - 辅助参考：Position Snapshot、实时 margin 数据
  - 最终裁定以 REST 为准
- **监控参数 / 指标**：
  - `maint_margin_rate`（= Binance `maintMarginRatio`，维持保证金占仓位总价值比例，值越高风险越大）
- **适用范围**：仅合约（Futures）— 单账户维度。Spot 无保证金机制，不适用
- **规则条件**：
  - `maint_margin_rate >= threshold`
- **阈值配置项**：
  - `threshold_1`（L2 预警线，初始建议值 5%，按账户级配置，不硬编码）
  - `threshold_2`（L3 严重线，初始建议值 8%，按账户级配置，不硬编码）
  - 阈值可能受账户模式、杠杆档位、持仓结构影响，需按账户维度可调
- **告警等级建议**：
  - L2（ALERT）：`maint_margin_rate >= threshold_1`，且连续 2 个窗口命中（或 2/3 窗口命中）
  - L3（CRITICAL）：`maint_margin_rate >= threshold_2`，若数据 Fresh 可即时触发；若数据非 Fresh，先二次 REST 确认再触发
- **系统动作建议**：
  - L2：Telegram-critical 高频预警
  - L3：Telegram 语音电话告警 + 人工确认
- **恢复条件建议**：
  - MMR 恢复至 threshold_1 以下，连续 2 个窗口
- **告警文案参考**：`【严重报警】{exchange} {account} 维持保证金占比 {value}% 超阈值 {threshold}%，距强平风险较近`
- **实现归属**：risk_platform
- **实现状态**：🔲 种子配置
- **待确认问题**：
  - 不同交易所 MMR 计算口径差异如何适配？（扩交易所时需处理）
  - 5% / 8% 作为初始建议值，是否需要按账户/杠杆档位差异化配置？
  - L3 后续迭代是否需要接自动动作（降级/暂停）？

## 1.2 L-002 ★ 爆仓距离过近

- **规则编号**：L-002
- **规则名称**：爆仓距离过近
- **优先级**：P0
- **规则层级**：一级：平台统一主规则库
- **来源规则**：RISK-ACC-007
- **★ 交易员收编**：★ 是
- **指标类型**：A — 实时可读 (RT)（liq_price + mark_price 均为 API 实时字段）
- **风险对象**：仓位（合约仓位，仓位级+方向级）
- **业务目的**：实时监控当前价格与强平价格的距离，防止意外爆仓。比 L-001 更接近"临门一脚"的结果指标，同时触发时值班优先级应高于 L-001。
- **数据来源**：
  - **主判定源**：交易所 Position API（`liquidationPrice` 字段）+ Mark Price（实时）
  - 辅助参考：Position Snapshot
- **监控参数 / 指标**：
  - `liq_price`（强平价格）
  - `mark_price`（标记价格）
  - `distance_pct = abs(liq_price - mark_price) / mark_price`
  - 本规则基于 liq_price 与 mark_price 的相对距离，仅用作距离告警，方向由仓位 side 决定（多头：mark_price 向下逼近 liq_price；空头：mark_price 向上逼近 liq_price）
- **适用范围**：仅合约（Futures）— 单账户 + 单仓位 + 单方向。liq_price 是合约/杠杆仓位概念，Spot 不适用。全仓/逐仓模式下 liq_price 计算逻辑不同，需分别适配
- **规则条件**：
  - `distance_pct <= threshold`
- **阈值配置项**：
  - `threshold_1`（L2 预警线，初始建议值 5%，币安合约默认值，非平台统一标准）
  - `threshold_2`（L3 严重线，初始建议值 2%，币安合约默认值，非平台统一标准）
  - 不同杠杆/品种波动率不同，应允许按 symbol 或账户级配置，不硬编码
- **告警等级建议**：
  - L2：`distance_pct <= threshold_1`
  - L3：`distance_pct <= threshold_2` → Telegram 语音电话告警
- **系统动作建议**：
  - L2：Telegram-critical 高频预警
  - L3：Telegram 语音电话告警
- **恢复条件建议**：
  - `distance_pct >= threshold_1`，**连续 2 个窗口**
- **告警文案参考**：`【电话报警】{exchange} {account} {symbol} {side} 爆仓距离 {distance_pct}% 低于阈值 {threshold}%，liq_price={liq_price} mark_price={mark_price}`
- **实现归属**：risk_platform
- **实现状态**：🔲 待开发
- **待确认问题**：
  - 全仓/逐仓模式下 liq_price 计算差异如何适配？
  - `distance_pct` 分母固定用 `mark_price` 是否为最终标准口径？
  - 5% / 2% 是否需要按 symbol 波动率差异化配置？
  - L3 后续迭代是否需要接主动减仓能力？
  - L-001 和 L-002 同时触发时的仲裁优先级如何定义？
- **确认状态**：

- **规则编号**：L-003
- **规则名称**：ADL 风险升高

  - **[后续]** L2：降级/暂停 + 减仓建议
- **恢复条件建议**：
  - ADL 等级回落至 threshold_1 以下，**连续 2 个窗口**
- **告警文案参考**：`【报警】{exchange} {account} {symbol} {side} ADL 等级 {value} 超阈值 {threshold}，存在自动减仓风险`

## 1.4 L-004 ★ 单边 OI 占比过高

- **规则编号**：L-004
- **规则名称**：单边 OI 占比过高
- **优先级**：P2
- **规则层级**：一级：平台统一主规则库
- **来源规则**：RISK-ACC-006
- **★ 交易员收编**：★ 是
- **指标类型**：C — 跨源衍生 (DRV)（我方持仓(Position API) ÷ 市场总OI(公共API)，跨源计算）
- **适用范围**：仅合约（Futures），单市场（交易对） + 按账户持仓模式分支判断
- **风险对象**：账户 + 市场 + 持仓方向
- **业务目的**：防止我方单方向持仓在市场 OI 中占比过高，增加被针对/流动性风险
- **数据来源**：
  - 主判定源：Position REST API（持仓量 + 持仓模式）
  - 辅助源：交易所 Open Interest 公共 API（市场总 OI）
  - REST 为最终裁定
- **持仓模式分支判断**（核心逻辑）：
  - **前置条件**：先读取 `position_mode`（单向 One-Way / 双向 Hedge）
  - **A. 单向持仓账户**：使用净持仓方向计算
    - `side = "LONG" if net_position > 0 else "SHORT"`
    - `ratio = abs(net_position) / oi`
    - 只产生一条告警（当前净方向）
  - **B. 双向持仓账户**：多空方向分别计算，不能净额相抵
    - `long_ratio = long_position / oi`
    - `short_ratio = short_position / oi`
    - 任一方向超阈值即触发，可能同时产生两条告警
- **监控参数 / 指标**：
  - `position_mode`（单向 One-Way / 双向 Hedge）
  - `net_position`（净持仓，单向模式下使用）
  - `long_position`（多头持仓量，双向模式下使用）
  - `short_position`（空头持仓量，双向模式下使用）
  - `oi`（市场总 OI，公共 API）
  - `ratio`（计算结果，分子取值依赖持仓模式）
- **规则条件**：
  - 单向：`abs(net_position) / oi >= threshold`
  - 双向：`long_position / oi >= threshold` 或 `short_position / oi >= threshold`
- **阈值配置项**：
  - `max_oi_ratio`（初始建议待交易员确认，账户+交易对级可配）
- **告警等级建议**：
  - L1：占比超限（任一方向）
- **系统动作建议**：
  - Telegram-info 低频预警
  - [后续] 自动降低该方向新单规模
- **恢复条件建议**：
  - OI 占比回落至阈值以下，连续 2 个窗口确认
- **告警文案参考**：
  - 单向：`【预警】{exchange} {account} {symbol} 净{side}头持仓占市场OI {ratio_pct}%，超阈值 {threshold}%`
  - 双向：`【预警】{exchange} {account} {symbol} {side}头持仓占市场OI {ratio_pct}%，超阈值 {threshold}%（双向持仓模式）`
- **实现归属**：risk_platform
- **实现状态**：🔲 待开发
- **已确认决策**：
  - ✅ 双向持仓模式下，多空同时超限 → **分别告警**（各自独立一条）
  - ✅ OI 数据刷新延迟容忍窗口：**1 分钟**（暂定），超过 1 分钟未刷新的 OI 数据视为 stale，跳过本轮判定
- **待确认问题**：
  - 不同交易所 OI 数据可得性和更新频率？

## 1.5 L-005 联合保证金/抵押物折价双杀

- **规则编号**：L-005
- **规则名称**：联合保证金/抵押物折价双杀
- **优先级**：P1（但 MVP 阶段不开发，条件未量化 + 数据源复杂度高）
- **MVP 状态**：❌ MVP 不纳入，后续版本开发
- **规则层级**：一级：平台统一主规则库
- **来源规则**：—
- **★ 交易员收编**：否
- **指标类型**：C — 跨源衍生 (DRV)（抵押物价格 + 折扣率配置 + 账户资产，多源组合）
- **适用范围**：仅合约（联合保证金 / Portfolio Margin 模式），仅对存在非稳定币抵押物的账户生效
- **风险对象**：账户（联合保证金模式）
- **业务目的**：防止联合保证金模式下抵押物价格下跌 + 折扣率恶化的"双杀"效应，导致有效保证金急剧缩水
- **数据来源**：
  - 主判定源：账户 Asset REST API（抵押物持仓 + 账户余额）
  - 辅助源：抵押物市场价格 Feed（如 BTC/ETH 价格）

## 2.1 E-001 ★ 净 Delta 过高

- **统一 USD 换算口径**（核心逻辑）：

  - **U 本位合约**：`delta_usd = position_qty × mark_price × contract_multiplier`（position_qty 带方向：正=多，负=空）

- **监控参数 / 指标**：

  - `delta_side`（净多 LONG / 净空 SHORT，由 net_delta_usd 符号决定）
  - `abs_net_delta_usd = abs(net_delta_usd)`（用于阈值判定）
- **计算层级与分层阈值**：
  - **账户级**：单账户内所有品种的 net_delta_usd，阈值 `max_net_delta_usd_account`
  - **账户组级**：同组所有账户聚合，阈值 `max_net_delta_usd_group`
  - **全局级**：所有账户聚合，阈值 `max_net_delta_usd_global`
  - 三个层级独立判定，各自可触发告警
- **规则条件**：
  - `abs(net_delta_usd) >= threshold`（按对应层级的阈值判定）
  - 条件方向：`>=`（绝对值越大风险越高）
- **阈值配置项**：

  - `max_net_delta_usd_global`（全局级，待确认）
- **告警等级建议**：
  - L1：轻度超限（如 >= threshold_1），Telegram-info 低频预警
  - L2：严重超限（如 >= threshold_2），Telegram-critical 高频预警

  - L2：`【严重预警】{scope} 净Delta {abs_delta_usd} USD（净{delta_side}），严重超限 {threshold} USD`
  - 其中 `{scope}` = 账户名 / 账户组名 / 全局

- **实现状态**：🔲 待开发

## 2.7 E-007 风险预算综合监控

- **规则编号**：E-007（合并原 E-008 使用率 + E-009 超限 + E-012 消耗速率）
- **规则名称**：风险预算综合监控
- **合并说明**：原 E-008（使用率预警）、E-009（预算超限）、E-012（消耗速率异常）本质上是同一风险预算数据管道的三个观测维度——水位、阈值档、速率。合并为一条规则，包含「水位维度」和「速率维度」两个子条件，独立判定、独立告警
- **优先级**：P2
- **规则层级**：一级：平台统一主规则库
- **来源规则**：—
- **★ 交易员收编**：否
- **指标类型**：B — 窗口聚合 (AGG)（累计损益 / 配置预算，治理型聚合指标）
- **适用范围**：现货 + U 本位合约（币本位合约暂不纳入）
- **风险对象**：策略 / 账户（按四级架构，预算可挂载在策略或账户层）
- **业务目的**：全方位监控风险预算健康度，包括两个维度：
  - **水位维度**：预算已用了多少（比例），在接近或超出预算时分级预警
  - **速率维度**：预算正在以多快的速度被消耗（前置动态指标），在"还没超限但正在快速接近超限"时提前预警
- **数据来源**：
  - 主判定源：PnL 计算服务（已实现 + 未实现损益）
  - 配置源：风险预算配置表（budget 金额 + 风险窗口周期）
- **`current_loss` 口径定义**（核心，两个维度共用）：
  - **含义**：风险窗口内的累计亏损金额
  - **计算方式**：在配置的风险窗口（如 24h / 7d / 30d）内，滚动累计 PnL
    - PnL > 0：盈利，不计入 loss（只关注亏损侵蚀预算）
    - PnL < 0：亏损，累加到 `current_loss`
    - `current_loss = abs(Σ min(pnl, 0))`（风险窗口内所有亏损的绝对值之和）
  - **包含范围**：已实现亏损 + 未实现亏损（mark-to-market）
  - **风险窗口**：可配置（如 rolling 24h / calendar day / rolling 7d），窗口滑出的亏损自动释放
- **监控参数 / 指标**：
  - `risk_window`（风险窗口周期，可配置：24h / 7d / 30d 等）
  - `current_loss`（风险窗口内累计亏损，按上述口径）
  - `risk_budget`（配置的风险预算金额，挂载在策略或账户层）
  - **水位维度**：
    - `risk_budget_usage = current_loss / risk_budget`（使用率，0~1+）
  - **速率维度**：
    - `budget_consumption_rate = (current_loss_t - current_loss_t_minus_N) / (N hours)`（滚动窗口内亏损增速，USD/h）
    - 或百分比表达：`budget_consumption_rate_pct = budget_consumption_rate / risk_budget`（预算消耗速率占预算比例，%/h）
    - 速率窗口：可配置（建议 1h 短窗口做快速预警，24h 窗口做趋势观测）
- **预算挂载层级**：
  - 预算可配置在**策略级**或**账户级**
  - MVP 先支持账户级预算（最简单、最直接）
  - 后续扩展策略级预算，需四级架构中策略→账户映射就绪
  - 子层级是否继承上层预算、是否可覆盖，待治理模型确定后再定
- **规则条件**（两个维度独立判定，任一触发即告警）：
  - **水位维度**：`risk_budget_usage >= threshold`（使用率越高越接近风险边界）
  - **速率维度**：`budget_consumption_rate_pct >= threshold`（消耗速率越快，越可能短期内打穿预算）
  - 两个维度独立触发、独立告警、独立恢复
- **阈值配置项**：
  - `risk_budget`（预算金额，按策略或账户级配置）
  - `risk_window`（风险窗口周期，如 24h）
  - **水位维度阈值**：
    - `budget_usage_warn_pct`（L1 预警线，如 70%，待确认）
    - `budget_usage_critical_pct`（L2 超限线，如 100%，待确认）
  - **速率维度阈值**：
    - `rate_window`（速率计算窗口，建议 1h，可配置）
    - `consumption_rate_warn_pct`（L1 速率预警线，如每小时消耗 5% 预算，待确认）
    - `consumption_rate_critical_pct`（L2 速率危险线，如每小时消耗 15% 预算，待确认）
- **告警等级建议**：
  - **水位维度**：
    - L1：使用率偏高（如 >= 70%），预警缓冲
    - L2：预算耗尽或超限（如 >= 100%），需立即干预
  - **速率维度**：
    - L1：消耗速率偏快（预警）
    - L2：消耗速率失控（照此速率短期内将打穿预算）
- **系统动作建议**：
  - L1：Telegram-info 低频预警
  - L2：Telegram-critical 高频预警
  - [后续] L2 触发时自动暂停该策略/账户交易
- **恢复条件建议**：
  - **水位维度**：使用率回落至预警线以下，连续 2 个窗口确认；或风险窗口滑动导致历史亏损释放；或人工追加预算/重置预算周期
  - **速率维度**：消耗速率回落至阈值以下，连续 2 个速率窗口确认（速率型指标天然抖动，必须加迟滞）
- **告警文案参考**：
  - 水位 L1：`【预警】{scope} 风险预算使用率 {usage_pct}%（{risk_window}窗口累亏 {current_loss} USD / 预算 {budget} USD）`
  - 水位 L2：`【严重预警】{scope} 风险预算已耗尽，使用率 {usage_pct}%（{risk_window}窗口累亏 {current_loss} USD / 预算 {budget} USD）`
  - 速率 L1：`【预警】{scope} 预算消耗速率 {rate_pct}%/h（近{rate_window}亏损 {delta_loss} USD），照此速率 {eta_hours}h 后将耗尽预算`
  - 速率 L2：`【严重预警】{scope} 预算消耗速率失控 {rate_pct}%/h，预算将在 {eta_hours}h 内耗尽`
  - 其中 `{scope}` = 策略名 / 账户名
- **实现归属**：risk_platform
- **实现状态**：🔲 待开发

## 2.8 E-008 Funding Rate Bleed

- **规则编号**：E-008
- **规则名称**：Funding Rate Bleed（资金费率慢性消耗）
- **优先级**：P2
- **规则层级**：一级：平台统一主规则库

- **★ 交易员收编**：否

- **业务目的**：监控合约仓位被资金费率持续侵蚀的风险。仓位本身不一定会爆，但 funding 会持续消耗利润/本金，尤其在长时间单边持仓时

  - 本条是 funding 风险的**累计损失版本**，关注"已经吃了多少"
  - 不覆盖"当前 funding 方向是否不利"或"下一次结算预计损失"等前瞻信号（如需后续可另建规则）

  - `cumulative_funding_loss`（窗口内累计 funding 支出 USD）

  - `annualized_funding_rate`（年化 funding 费率，主判定指标）
  - `annualized_funding_cost`（年化 funding 成本 USD，辅助参考）
- **规则条件**：
  - `annualized_funding_rate >= threshold`（年化费率超限）
  - 条件方向：`>=`（年化成本越高越危险）
- **阈值配置项**：
  - `funding_window`（统计窗口，建议默认 3d，待确认）

  - 连续 2 个结算周期确认
  - 注意：累计损失不会自己"回落"，恢复依赖窗口滑动或仓位变化，不能照搬"回落到阈值以下"

## 2.9 E-009 资金周期对账差异

- **规则编号**：E-009
- **规则名称**：资金周期对账差异

## 3.1 S-001 ★ 公共数据订阅断联/延迟

- **规则编号**：S-001
- **规则名称**：公共数据订阅断联/延迟
- **优先级**：P0
- **规则层级**：一级：平台统一主规则库
- **来源规则**：RISK-SYS-001
- **★ 交易员收编**：★ 是
- **指标类型**：D — 系统自观测 (SYS)（WS 连接管理器需要暴露连接状态、延迟、重连计数、业务数据鲜活度）
- **适用范围**：每交易所 × 每数据类型（orderbook / trades / ticker）为主监控粒度
- **风险对象**：交易所 × 数据类型（orderbook / trades / ticker）
- **业务目的**：监控公共数据 WebSocket 订阅健康状态，防止行情数据断流导致风控失效
- **规则定位说明**：
  - **核心设计原则：全量观测，分层告警**
    - 全量 WS 订阅都记录健康状态（每个 symbol、每个 channel）
    - 但不对所有 symbol 等权逐条告警，否则网络抖动会造成告警风暴
    - 告警主入口按分层设计，避免噪音淹没真正严重的问题
  - **MVP 监控三层架构**：
    - **第 1 层（连接层）**：按 交易所 × 公共 WS 连接 监控——连接是否存活、心跳是否正常、重连次数。这是最基础的一层
    - **第 2 层（数据类型层，本条主层级）**：按 交易所 × 数据类型 监控——某类公共数据（orderbook / trades / ticker）整体是否有更新。不是每个 symbol 一条规则，而是看该类数据整体健康度
    - **第 3 层（关键标的层）**：只对核心 symbol 白名单做更细监控（如 BTCUSDT、ETHUSDT、当前主交易对）。因为有些场景下连接还活着、ticker 有消息，但核心交易对 orderbook 实际断了
  - 三层任一异常均可触发告警，但告警级别不同
- **数据来源**：
  - WS 连接管理器暴露的连接状态、心跳、重连计数（连接层）
  - 各数据类型最近消息时间戳（数据类型层）
  - 核心 symbol 白名单各自的最近更新时间戳（关键标的层）
- **监控参数 / 指标**：
  - **A. 连接健康参数**（第 1 层）：
    - `ws_public_connected`（bool，连接是否存活）
    - `ws_public_heartbeat_gap_ms`（距上次心跳的间隔）
    - `ws_public_reconnect_count`（滚动窗口内重连次数）
    - `ws_public_latency_ms`（消息往返延迟）
  - **B. 业务数据鲜活参数**（第 2~3 层）：
    - `ws_public_last_business_update_ts`（某数据类型最近一条业务消息的时间戳）
    - `ws_public_data_gap_ms`（= now - last_business_update_ts，数据断流时长）
    - `ws_critical_symbol_last_update_ts`（核心 symbol 白名单的最近更新时间戳）
  - 关键区分：连接层参数正常 ≠ 业务数据正常。连接没断、心跳在，但业务数据可能卡住（静默断流），必须同时监控两类参数
- **规则条件**（任一满足即触发）：
  - 连接层：`ws_public_connected == false` 或 `ws_public_heartbeat_gap_ms >= heartbeat_threshold`
  - 数据类型层：`ws_public_data_gap_ms >= data_stale_threshold`（某类数据整体无更新超时）
  - 关键标的层：`ws_critical_symbol_data_gap_ms >= critical_symbol_threshold`（核心 symbol 无更新超时）
  - 辅助条件：`ws_public_reconnect_count >= max_reconnect`（短时频繁重连）
  - 延迟条件：`ws_public_latency_ms >= latency_threshold`
  - 条件方向：`>=`（间隔/延迟/重连越大越危险）
- **阈值配置项**：
  - `heartbeat_threshold`（心跳超时，如 10s）
  - `data_stale_threshold`（数据类型断流超时，如 10s，按交易所×数据类型级可配）
  - `critical_symbol_threshold`（核心 symbol 断流超时，如 5s，按 symbol 级可配）
  - `latency_threshold`（延迟阈值，如 5s）
  - `max_reconnect`（滚动窗口内最大重连次数，如 5 次/分钟）
  - `critical_symbol_whitelist`（核心 symbol 白名单，可配置）
- **告警等级建议**：
  - L1：单个数据类型数据断流 > threshold，或核心 symbol 无更新 > threshold（预警，可能是临时抖动）
  - L2：单个交易所单个数据类型持续断联 > 10s，或延迟持续 > 5s，或频繁重连（风控数据可信度受损）
  - L3：同一交易所多个数据类型同时断联 > 30s → 全面失明风险，需升级联动 S-002
- **系统动作建议**：
  - L1：Telegram-info 低频预警
  - L2：Telegram-critical 高频预警
  - L3：Telegram 语音电话
  - **[后续]** L2：告警 + 标记数据不可信（downstream 规则可据此降级置信度）
  - **[后续]** L3：暂停该交易所相关策略
- **恢复条件建议**：
  - WS 恢复连接 且 业务数据恢复更新（两个条件都要满足，不能只看连接层）
  - 连续 2 个检测周期确认
- **告警文案参考**：
  - L1：`【预警】{exchange} {data_type} 公共数据 {gap_seconds}s 无更新`
  - L2：`【报警】{exchange} {data_type} WS 断联 {gap_seconds}s，已重连 {reconnect_count} 次未恢复`
  - L2（核心标的）：`【报警】{exchange} {symbol} orderbook {gap_seconds}s 无更新（核心标的）`
  - L3：`【电话报警】{exchange} 多类数据同时断联 > 30s，公共数据全面失明`
- **实现归属**：risk_platform
- **实现状态**：🔲 待开发

  - ✅ 核心设计原则：全量观测，分层告警（不对所有 symbol 等权逐条报警）

## 3.3 S-003 ★ 风控只读 API 频控使用率过高/耗尽

- **规则编号**：S-003
- **规则名称**：风控只读 API 频控使用率过高/耗尽
- **优先级**：P1
- **规则层级**：一级：平台统一主规则库
- **来源规则**：RISK-SYS-001
- **★ 交易员收编**：★ 是
- **指标类型**：D — 系统自观测 (SYS)（从 API 响应头解析，需要 HTTP client 采集）
- **适用范围**：每交易所 × 每只读 API Key（风控系统自身使用的 Key）
- **风险对象**：风控系统只读 API Key / IP
- **业务目的**：监控风控系统自身只读 API 的频控使用率，防止风控被限流导致真相源刷新失败、系统失明
- **规则定位说明**：
  - **架构约束：风控与交易隔离**
    - 风控系统使用的是**只读 API Key**（查仓位、查余额、查订单、对账、刷新真相源）
    - 交易执行使用的是**交易 API Key**（下单、撤单等写操作）
    - 两者不是同一个 Key，也不是同一个频控池
    - **本条规则只监控风控自身只读 Key 的频控消耗，不监控交易执行链路**
  - **为什么不监控交易 API Key**：
    - 风控系统无法也不应该直接观测交易 API Key 的使用情况
    - 直接接入交易 Key 会破坏风控/交易隔离原则，扩大权限面
    - 即使只是"读监控"，也容易把系统耦合到交易执行层
  - **后续扩展路径（交易 API 频控遥测）**：
    - 如果未来需要监控交易 API 的频控情况，合理的方式是：交易引擎/外部策略侧自行采集频控使用率，以遥测指标（usage_pct, remaining, reset_time）上报给风控
    - 风控只消费遥测指标，不接触交易 Key 本身——这样不破坏隔离
    - 这属于二阶段能力，不纳入当前版本的默认假设
- **数据来源**：
  - 风控系统 HTTP Client 发出 REST 请求后，从响应头中解析 rate limit 信息
  - 典型字段：`X-MBX-USED-WEIGHT-*`（Binance）、`x-ratelimit-remaining`（OKX）等
  - 自身请求计数器（滚动窗口内的请求次数统计）
- **监控参数 / 指标**：
  - `rate_limit_usage_pct`（当前频控使用率，0~100%）
  - `remaining_requests`（剩余可用请求数）
  - `reset_time`（频控重置时间点）
  - `request_count_1m`（风控自身 1 分钟内的请求次数，自行统计）
- **规则条件**：
  - `rate_limit_usage_pct >= threshold`（频控使用率过高）
  - 或 `remaining_requests <= min_remaining`（剩余配额过低）
  - 条件方向：usage `>=`（越高越危险），remaining `<=`（越低越危险）
- **阈值配置项**：
  - `rate_limit_warn_pct`（L1 预警线，建议 70%，待确认）
  - `rate_limit_critical_pct`（L2 危险线，建议 90%，待确认）
  - `min_remaining_requests`（最低剩余请求数，按交易所级可配）
  - 阈值按 交易所 × API Key 级可配（不同交易所 rate limit 规则差异大）
- **告警等级建议**：
  - L1：使用率偏高（如 >= 70%），预警——风控系统可能需要降频
  - L2：使用率危险（如 >= 90%）或剩余配额极低——风控即将被限流，真相源刷新面临中断
- **系统动作建议**：
  - L1：Telegram-info 低频预警
  - L2：Telegram-critical 高频预警
  - **[MVP]** L2 触发时进入"配额保命模式"：降低非关键 REST 轮询频率，优先保障关键数据（仓位、余额）的刷新
  - **[后续]** 自动降频策略（按 endpoint 优先级分级限流）
- **恢复条件建议**：
  - 使用率回落至预警线以下（`rate_limit_usage_pct < warn_pct`）
  - 或 `remaining_requests` 恢复到安全水位
  - 连续 2 个检测周期确认
- **告警文案参考**：
  - L1：`【预警】{exchange} 风控只读API频控使用率 {usage_pct}%（剩余 {remaining} 请求），接近限流`
  - L2：`【报警】{exchange} 风控只读API频控 {usage_pct}%，即将被限流！已进入配额保命模式`

  - ✅ 架构隔离：风控不接触交易 API Key，不破坏风控/交易隔离原则
  - ✅ 后续如需监控交易 API，通过遥测指标上报方式接入，不直接接触交易 Key
